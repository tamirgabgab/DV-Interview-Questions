## השאלה

ה-DUT מקבל בקשות קריאה, כל אחת עם `id` (0 עד 15) וכתובת, ומחזיר תשובה עם אותו `id`
והנתון. הכלל של הממשק, כמו ב-AXI : תשובות **לאותו `id`** חוזרות לפי סדר הבקשות, ותשובות
ל-`id` שונים יכולות להגיע בכל סדר. מודל ייחוס נותן לכל בקשה, ברגע שהיא נשלחת, את
הנתון שהתשובה שלה צריכה להחזיר.

- **סעיף א – התכנון :** תכננו את ה-scoreboard : באיזה מבנה נתונים שומרים את מה שמחכה
  לתשובה, מה בודקים בכל תשובה, ומה בודקים בסוף הטסט. כתבו אותו.
- **סעיף ב – למה לא פשוט יותר :** שני מהנדסים מציעים חלופות : "תור אחד לכל הבקשות",
  ו"לכל תשובה, לחפש בתור של ה-`id` שלה בקשה עם אותו נתון". מה כל אחת תפספס, ומה כל אחת
  תדווח בטעות?
- **סעיף ג – איפוס, זמן וכיסוי :** מה קורה ל-scoreboard כשה-DUT מתאפס באמצע תעבורה?
  איך תופסים תשובה שלא מגיעה אף פעם? ואיך יודעים שהטסט בכלל בדק ערבוב בין `id`-ים?

??? interviewer "מה המראיין בודק"
    - **הכלל של הממשק כמבנה נתונים :** האם המועמד מתרגם "בסדר בתוך `id`, חופשי בין
      `id`-ים" ישירות למבנה, ולא כותב חיפוש כללי שמקבל יותר ממה שמותר.
    - **שני סוגי טעויות :** אזעקת שווא על התנהגות חוקית, ופספוס של באג. האם הוא בודק את
      התכנון מול שניהם.
    - **מה שלא קורה :** תשובה חסרה ותשובה שלא מגיעה בזמן לא מופיעות באף השוואה; צריך
      בדיקה בסוף ובדיקת זמן.
    - **מחזור החיים :** איפוס באמצע, תשובות "ישנות" אחריו, וניקוי בסוף הטסט.
    - **כיסוי :** סביבה שעוברת בלי לבדוק את המקרה הקשה לא הוכיחה כלום.

### סעיף א – התכנון

??? tip "רמז 1"
    הכלל הוא "בסדר בתוך כל `id`". איזה מבנה שומר על סדר? וכמה כאלה צריך?

??? tip "רמז 2"
    מערך אסוציאטיבי שהמפתח שלו `id`, וכל ערך הוא תור. מה עושים כשמגיעה תשובה ל-`id` שהתור
    שלו ריק? ומה נשאר לבדוק כשהטסט נגמר?

??? success "פתרון סעיף א"
    !!! answer "תשובה בקצרה"
        תור לכל `id` (מערך אסוציאטיבי של תורים). בקשה מכניסה לסוף התור של ה-`id` שלה את
        הנתון הצפוי ואת הזמן. תשובה נבדקת **רק מול ראש התור** של ה-`id` שלה : תור ריק
        הוא תשובה לא צפויה, נתון שונה הוא אי-התאמה. בכל מחזור בודקים שאף בקשה לא מחכה
        יותר מ-timeout, ובסוף הטסט כל התורים חייבים להיות ריקים.

    <!-- cost: תשובה \( O(1) \) | זיכרון \( O(\text{outstanding}) \) -->

    #### הרעיון { .sol-idea }

    הכלל של הממשק אומר בדיוק מה מותר : בין `id`-ים אין סדר, ובתוך `id` יש. מבנה הנתונים
    צריך להגיד את אותו הדבר, לא פחות ולא יותר. **תור לכל `id`** עושה את זה : התשובה הבאה
    של `id` מסוים חייבת להיות זו שבראש התור שלו, וכל תור אחר לא משנה.

    ההשוואה היא רק חצי מהעבודה. שלושה באגים לא מופיעים באף השוואה : תשובה שלא הגיעה
    (בסוף הטסט התור לא ריק), תשובה שמגיעה מאוחר מדי (בדיקת זמן על כל בקשה ממתינה),
    ותשובה בלי בקשה (התור ריק כשהיא מגיעה).

    #### השלבים { .sol-steps }

    <div class="steps" markdown>

    1. **בקשה (מהמוניטור של הכניסה) :** מכניסים לסוף `pending[id]` את הנתון שהמודל צופה
       ואת הזמן.
    2. **תשובה (מהמוניטור של היציאה) :** אם `pending[id]` ריק, זו תשובה לא צפויה. אחרת
       מוציאים את הראש ומשווים.
    3. **זמן :** בכל מחזור, כל בקשה שמחכה יותר מ-timeout מדווחת פעם אחת.
    4. **סוף הטסט (`check_phase`) :** כל מה שנשאר בתורים הוא תשובה חסרה.
    5. **איפוס :** מרוקנים את כל התורים (סעיף ג).

    </div>

    #### הקוד { .sol-code }

    הקוד כתוב כמחלקה רגילה, כדי שירוץ בכל סימולטור. ב-UVM היא יורשת מ-`uvm_scoreboard`, שתי
    הפונקציות הראשונות הן ה-`write` של שני `uvm_analysis_imp` (עם `` `uvm_analysis_imp_decl ``),
    ו-`final_check` נקראת מ-`check_phase`.

    === "SystemVerilog"
        ```systemverilog title="class ooo_scoreboard" linenums="1" hl_lines="3 15 22 25 34 40"
        class ooo_scoreboard;
          typedef struct { int data; longint t; bit late; } exp_t;
          exp_t   pending[int][$];                      // (1)!
          string  errors[$];
          longint timeout;

          function new(longint timeout = 1000);
            this.timeout = timeout;
          endfunction

          // from the request monitor: the data the reference model expects, and the time
          function void on_request(int id, int data, longint now);
            exp_t e;
            e.data = data; e.t = now; e.late = 0;
            pending[id].push_back(e);
          endfunction

          // from the response monitor
          function void on_response(int id, int data, longint now);
            exp_t e;
            if (!pending.exists(id) || pending[id].size() == 0) begin
              errors.push_back($sformatf("unexpected response id=%0d at %0d", id, now));   // (2)!
              return;
            end
            e = pending[id].pop_front();                  // (3)!
            if (e.data != data)
              errors.push_back($sformatf("mismatch id=%0d: got %0d, expected %0d", id, data, e.data));
          endfunction

          // every cycle: a request that waits longer than the timeout is reported once
          function void check_timeouts(longint now);
            foreach (pending[id, k])
              if (!pending[id][k].late && now - pending[id][k].t > timeout) begin
                pending[id][k].late = 1;                  // (4)!
                errors.push_back($sformatf("timeout id=%0d: waiting since %0d", id, pending[id][k].t));
              end
          endfunction

          function void on_reset();
            pending.delete();                             // (5)!
          endfunction

          // check_phase: whatever is left was never answered
          function void final_check();
            foreach (pending[id, k])
              errors.push_back($sformatf("missing response id=%0d, requested at %0d", id, pending[id][k].t));
          endfunction
        endclass
        ```

        1. מערך אסוציאטיבי לפי `id`, וכל איבר בו הוא תור. ה-`id`-ים נוצרים רק כשהם בשימוש.
        2. תור ריק : תשובה בלי בקשה, כפולה, או ישנה מלפני איפוס.
        3. רק ראש התור. זה מה שהופך "בסדר בתוך `id`" לבדיקה, ולא להנחה.
        4. הדגל מונע דיווח חוזר בכל מחזור. אפשר גם לעצור את הטסט כאן (`uvm_fatal`).
        5. כל מה שחיכה לפני האיפוס לא יקבל תשובה. ראו סעיף ג.

    === "Python"
        ```python title="class OooScoreboard" linenums="1" hl_lines="7 16 18 25 30"
        from collections import defaultdict, deque


        class OooScoreboard:
            def __init__(self, timeout: int = 1000):
                self.timeout = timeout
                self.pending = defaultdict(deque)   # (1)!
                self.errors: list[str] = []

            def on_request(self, id: int, data: int, now: int) -> None:
                self.pending[id].append([data, now, False])   # expected data, time, reported late

            def on_response(self, id: int, data: int, now: int) -> None:
                q = self.pending.get(id)
                if not q:
                    self.errors.append(f"unexpected response id={id} at {now}")   # (2)!
                    return
                exp, _, _ = q.popleft()                         # (3)!
                if exp != data:
                    self.errors.append(f"mismatch id={id}: got {data}, expected {exp}")

            def check_timeouts(self, now: int) -> None:
                for id, q in self.pending.items():
                    for e in q:
                        if not e[2] and now - e[1] > self.timeout:
                            e[2] = True
                            self.errors.append(f"timeout id={id}: waiting since {e[1]}")

            def on_reset(self) -> None:
                self.pending.clear()

            def final_check(self) -> None:
                for id, q in self.pending.items():
                    self.errors += [f"missing response id={id}, requested at {t}" for _, t, _ in q]
        ```

        1. תור לכל `id`, שנוצר בפעם הראשונה שה-`id` מופיע.
        2. ‏`get` לא יוצר תור חדש, ותור ריק הוא `False` : תשובה בלי בקשה.
        3. רק ראש התור של ה-`id`, כמו בגרסת ה-SystemVerilog.

    #### למה זה נכון { .sol-proof }

    **אין אזעקות שווא.** אם ה-DUT חוקי, התשובות של כל `id` מגיעות בסדר הבקשות שלו, ולכן
    כל תשובה פוגשת בראש התור שלה את הבקשה שהיא עונה עליה. ערבוב בין `id`-ים לא נוגע
    בסדר של אף תור.

    **אין פספוסים.** כל הפרה של הכלל נתפסת באחת מארבע הבדיקות : תשובה מוקדמת מדי בתוך
    `id` פוגשת בראש התור בקשה אחרת (אי-התאמה, אלא אם שתי הבקשות צופות אותו נתון; לכן
    המודל משאיר בנתון משהו שמזהה את הבקשה, למשל את הכתובת); תשובה בלי בקשה פוגשת תור
    ריק; תשובה חסרה נשארת בתור עד הסוף; תשובה תקועה נתפסת ב-timeout.

    **הבדיקה הזו בטסטים של השאלה.** הקוד רץ מול שלושה בודקים שנכתבו בנפרד, על כל
    התרחישים של סעיף ב ועל אלפי זרמים אקראיים : זרמים חוקיים, וזרמים שהוכנס בהם באג
    אחד (החלפה בתוך `id`, נתון שגוי, תשובה חסרה או כפולה, עיכוב). הוא עובר את כל
    החוקיים ומדווח על כל המקולקלים.

### סעיף ב – למה לא פשוט יותר

??? tip "רמז 1"
    בדקו כל חלופה מול שני תרחישים : ערבוב חוקי בין `id`-ים, והחלפת סדר בתוך `id` אחד.

??? tip "רמז 2"
    "לחפש בתור" מקבל תשובה שנמצאת **איפשהו** בתור. מה אם היא לא בראש?

??? success "פתרון סעיף ב"
    !!! answer "תשובה בקצרה"
        תור אחד לכולם נכשל על ערבוב **חוקי** בין `id`-ים : אזעקת שווא, והטסטים נכבים או
        שמישהו "מתקן" את ה-DUT. חיפוש בכל התור של ה-`id` מקבל תשובה שהקדימה בקשה מוקדמת
        יותר של אותו `id` : **פספוס** של בדיוק הבאג שהכלל נועד למנוע. רק תור לכל `id` עם
        השוואה לראש התור מתאים לכלל.

    #### הרעיון { .sol-idea }

    בודק טוב מקבל **בדיוק** את מה שהממשק מתיר. תור אחד מתיר פחות מהממשק (הוא דורש סדר גם
    בין `id`-ים), ולכן הוא מדווח על התנהגות חוקית. חיפוש מתיר יותר מהממשק (הוא מקבל כל
    סדר בתוך `id`), ולכן הוא מקבל התנהגות לא חוקית. שתי הטעויות יקרות : הראשונה מבזבזת
    זמן ומלמדת את הצוות להתעלם מכשלונות, והשנייה משחררת באג לסיליקון.

    #### השלבים { .sol-steps }

    <div class="steps" markdown>

    1. **מה מותר :** לכתוב את הכלל של הממשק כטבלה : מה חוקי, מה לא.
    2. **מה הבודק מקבל :** לכל תכנון, לשאול על כל שורה בטבלה אם הוא מקבל אותה.
    3. **תרחישים קטנים :** תרחיש של 3 עד 5 אירועים לכל שורה, ולהריץ עליו את הבודק.
    4. **זרם אקראי :** להשוות את הבודק לזרמים חוקיים ולזרמים עם באג מוזרק אחד.

    </div>

    #### למה זה נכון { .sol-proof }

    **התרחישים.** כל תרחיש הוא כמה אירועים, וכל עמודה היא בודק אחר עם אותן בדיקות סוף
    וזמן. ‏✓ פירושו שהבודק צדק, ‏✗ שהוא טעה :

    שתי השורות הראשונות הן כל הסיפור : תור אחד נכשל על הראשונה, והחיפוש עובר את השנייה.
    בשאר השורות כל השלושה צודקים, כי הבאג נתפס בבדיקות שמשותפות לכולם. גם כשתור אחד
    "תופס", הוא לפעמים מצביע על המקום הלא נכון : בתשובה החסרה הוא מדווח קודם אי-התאמה
    על `id` 1, שדווקא ענה נכון.

    **נסו בעצמכם.** בוחרים תרחיש, או זרם אקראי עם באג מוזרק, ועוברים אירוע אחרי אירוע.

### סעיף ג – איפוס, זמן וכיסוי

??? tip "רמז 1"
    אחרי איפוס, האם ה-DUT עוד יענה על בקשות ששלחו לפניו? ומה ה-scoreboard יעשה אם כן?

??? tip "רמז 2"
    כיסוי של "ערבוב" הוא אירוע שה-scoreboard רואה : תשובה שהגיעה לפני תשובה של `id` אחר
    שהתבקשה קודם.

??? success "פתרון סעיף ג"
    !!! answer "תשובה בקצרה"
        באיפוס מרוקנים את כל התורים, וכל תשובה שמגיעה אחרי זה לבקשה ישנה נתפסת כ"לא צפויה".
        תשובה שלא מגיעה נתפסת ב-timeout בזמן הריצה (עם הזמן שהבקשה נשלחה), ובסוף הטסט
        ב-`final_check`. לכיסוי מודדים בתוך ה-scoreboard את מה שקרה בפועל : כמה תשובות
        עקפו בקשה ותיקה יותר של `id` אחר, כמה `id`-ים חיכו בבת אחת, ועומק התורים.

    #### הרעיון { .sol-idea }

    **איפוס.** האיפוס מבטל כל עסקה פתוחה, ולכן מה שחיכה לפניו לא אמור לקבל תשובה.
    ה-scoreboard צריך לשמוע על האיפוס (מהמוניטור, או מ-`reset_phase`) ולרוקן את התורים
    **באותו רגע**. מוקדם מדי : תשובה חוקית מלפני האיפוס תיראה לא צפויה. מאוחר מדי : תשובה
    ישנה תתקבל, ו"תשובה ישנה אחרי איפוס" היא באג אמיתי ונפוץ.

    **זמן.** בדיקת סוף לבד מוצאת תשובה חסרה רק בסוף, אחרי שהטסט אולי נתקע ב-timeout כללי בלי
    הסבר. בדיקת זמן לכל בקשה אומרת איזה `id` נתקע ומאיזה זמן, וזה מה שמקצר את ה-debug.

    **כיסוי.** טסט שבו ה-DUT תמיד עונה לפי סדר הבקשות עובר בכל אחד משלושת הבודקים, ולא
    הוכיח שום דבר על ערבוב. לכן ה-scoreboard סופר את מה שקרה : "תשובה עקפה בקשה ותיקה
    יותר של `id` אחר", מספר ה-`id`-ים שחיכו בבת אחת, ומספר הבקשות הממתינות. אלה
    coverpoints, ובלי שהם מכוסים הטסט לא סיים את העבודה.

    #### השלבים { .sol-steps }

    <div class="steps" markdown>

    1. **איפוס :** ‏`on_reset` מרוקן את כל התורים, מקריאה של המוניטור באותו מחזור שבו
       האיפוס נדגם.
    2. **אחרי איפוס :** תשובה לבקשה מלפני האיפוס נתפסת כ"לא צפויה", ובקשות חדשות נבדקות
       כרגיל.
    3. **זמן :** ‏`check_timeouts` בכל מחזור, עם timeout שנגזר מהמפרט ולא מניחוש.
    4. **כיסוי :** בכל תשובה בודקים אם יש בקשה ממתינה של `id` אחר שנשלחה קודם, וסופרים
       עקיפה; דוגמים את מספר ה-`id`-ים הפעילים ואת עומק התורים.

    </div>

    #### למה זה נכון { .sol-proof }

    **שני התרחישים האחרונים בטבלה של סעיף ב** הם בדיוק המקרים של האיפוס : בקשה חדשה אחרי
    האיפוס נענית ונבדקת כרגיל, ותשובה ישנה אחריו נתפסת כ"לא צפויה". בלי `on_reset`
    התשובה הישנה הייתה מתקבלת, והבקשה של `id` 1 מלפני האיפוס הייתה מדווחת כחסרה, שתי
    טעויות בבת אחת.

    **‏timeout לעומת בדיקת סוף.** שתיהן נחוצות : ה-timeout מוצא תשובה תקועה בזמן אמת,
    ובדיקת הסוף מוצאת בקשות שנשלחו קרוב לסוף הטסט ולא הספיקו להגיע ל-timeout.

## נקודות חשובות ושאלות המשך

??? trap "מלכודת : לקבל תשובה מה-driver במקום מהמוניטור"
    ה-scoreboard צריך לראות מה **באמת** עבר בממשק. אם הבקשה נלקחת מה-sequence או מה-driver,
    בקשה שה-driver לא הצליח לשלוח (backpressure, איפוס) תיראה כחסרה, ובאג של ה-driver
    עצמו לא ייתפס.

??? trap "מלכודת : נתון צפוי שלא מזהה את הבקשה"
    אם שתי בקשות של אותו `id` צופות את אותו נתון (למשל שתיהן קוראות אפס), החלפה ביניהן
    לא נראית. שומרים בפריט גם את הכתובת (או tag פנימי), ובודקים גם אותה כשהממשק מחזיר
    אותה.

??? trap "מלכודת : רק בדיקת סוף"
    טסט שנתקע בגלל תשובה שלא הגיעה ייגמר ב-timeout כללי של הסימולציה, בלי לדעת איזה
    `id` ומאיזה זמן. בדיקת זמן לכל בקשה נותנת את זה מיד.

??? followup "שאלות המשך"
    - **סדר חופשי גם בתוך `id` :** מה משתנה כשהממשק מתיר כל סדר, אבל התשובה מחזירה tag
      ייחודי?

        ??? fu-answer "תשובה"
            המפתח הוא ה-tag ולא ה-`id` : מערך אסוציאטיבי tag → פריט צפוי, ובדיקה ש-tag לא
            נמצא בשימוש פעמיים. ה-tag הוא שמזהה את הבקשה, ולכן אין צורך בסדר.

    - **תשובה בכמה חלקים :** כל קריאה חוזרת ב-4 beats (burst), ו-beats של `id`-ים שונים יכולים
      להשתלב. איך?

        ??? fu-answer "תשובה"
            בתור של כל `id` הפריט שבראש מחזיק מונה של ה-beats שהגיעו; מוציאים אותו רק ב-beat
            האחרון (`last`), ובודקים ש-`last` מגיע בדיוק אחרי 4.

    - **מודל שלא יודע את הנתון מראש :** הנתון תלוי בכתיבות שעוד לא הסתיימו. איפה מחשבים
      את הצפוי?

        ??? fu-answer "תשובה"
            ברגע התשובה, לא ברגע הבקשה : התור שומר את הכתובת, והמודל מחשב את הנתון לפי סדר
            הסיום של הכתיבות, או מחזיר קבוצה של ערכים חוקיים כשהסדר לא מוגדר.

    - **ביצועים :** ‏100,000 בקשות ממתינות. מה עולה הכי הרבה בקוד?

        ??? fu-answer "תשובה"
            ‏`check_timeouts` שעובר על כל הממתינים בכל מחזור. מספיק לבדוק את ראש כל תור (הוא
            הוותיק ביותר של ה-`id`), או להחזיק תור עדיפויות לפי זמן.
