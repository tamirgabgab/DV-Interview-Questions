## השאלה

לפניכם שלושה קטעים קצרים של RTL. כל אחד מהם עובר קומפילציה בלי שגיאה, ובכל אחד הסימולציה
מראה משהו אחר ממה שהמתכנן רצה. לכל קטע נתונים הכוונה של המתכנן, הקוד וצורת הגל מהסימולציה
(ריצה של Verilator). בכל סעיף : מצאו את הבאג, הסבירו מחזור אחרי מחזור איך הוא יוצר בדיוק את
צורת הגל הזו, ותקנו אותו.

איך לקרוא את צורות הגל : מחזור מתחיל בעלייה של `clk`, והשורה `cycle` ממספרת את המחזורים.
הכניסות מגיעות מרגיסטרים, ולכן הן מתחלפות מיד אחרי העלייה, והעלייה הבאה היא שדוגמת אותן.
רגיסטר מראה במחזור את מה שנכתב בו בעלייה שפתחה את המחזור. Verilator, בהגדרות ברירת המחדל,
מתחיל כל משתנה ב-0.

??? interviewer "מה המראיין בודק"
    - **קריאה של צורת גל מול הכוונה :** לא "משהו לא עובד", אלא באיזה מחזור, באיזה אות ובכמה
      הוא שונה ממה שהמתכנן רצה.
    - **החוק של השפה :** מאחורי כל באג כאן עומד חוק אחד של SystemVerilog. המראיין רוצה לשמוע
      את החוק, לא ניחוש שמזיז תו עד שהגל נראה נכון.
    - **הסבר מחזור אחרי מחזור :** איך הקוד, שורה אחרי שורה, נותן בדיוק את הערכים שבגל, כולל
      המחזורים שבהם הבאג לא נראה.
    - **מה הכלים תופסים :** אילו מהבאגים lint מוצא, באיזו אזהרה, ואילו עוברים בשקט.
    - **תיקון שמחזיק :** תיקון שנכון בגלל החוק ולא רק על הקלט הזה, ובדיקה שמראה את זה.

### סעיף א – קו השהיה של שלושה מחזורים

המתכנן רצה ש-`q3` יהיה `d` מושהה בשלושה מחזורי שעון, דרך שני רגיסטרים פנימיים, `q1` ו-`q2` :

```systemverilog title="delay3.sv" linenums="1"
module delay3 (
  input  logic clk,
  input  logic d,
  output logic q3
);
  logic q1, q2;

  always_ff @(posedge clk) begin
    q1 = d;
    q2 = q1;
    q3 = q2;
  end
endmodule
```

בסימולציה, עם `q1` ו-`q2` הפנימיים :

<!-- gen 0 -->

```wavedrom
{ signal: [
  { name: "clk",   wave: "p......." },
  { name: "cycle", wave: "========", data: ["0", "1", "2", "3", "4", "5", "6", "7"] },
  { name: "d",     wave: "01.010.." },
  { name: "q1",    wave: "0.1.010." },
  { name: "q2",    wave: "0.1.010." },
  { name: "q3",    wave: "0.1.010." }
]}
```

<!-- /gen -->

הכניסה `d` עולה במחזור 1, ולכן `q3` היה צריך לעלות במחזור 4. הוא עולה כבר במחזור 2, ו-`q1`,
‏`q2` ו-`q3` זהים בכל מחזור. מה הבאג, ואיך הוא יוצר את צורת הגל הזו?

??? tip "רמז 1"
    בשרשרת של רגיסטרים כל שלב מאחר בעוד מחזור, אבל כאן שלוש השורות זהות. איזה ערך של `q1`
    השורה `q2 = q1` קוראת : את זה שהיה לפני העלייה, או את זה שהשורה שמעליה כתבה הרגע?

??? tip "רמז 2"
    ב-SystemVerilog יש שתי השמות : ‏`=` ו-`<=`. מתי כל אחת מהן מעדכנת את הצד השמאלי?

??? success "פתרון סעיף א"
    !!! answer "תשובה בקצרה"
        ‏`=` היא השמה חוסמת (blocking) : היא כותבת מיד, והשורה הבאה כבר קוראת את הערך החדש. לכן
        בכל עלייה `d` עובר את שלוש השורות בבת אחת, ושלושת הרגיסטרים מקבלים את `d` של המחזור
        הקודם : השהיה של מחזור אחד. התיקון : ‏`<=` בשלוש השורות.

    #### הרעיון { .sol-idea }

    בעלייה של `clk` הבלוק רץ פעם אחת, שורה אחרי שורה. עם `=` כל שורה כותבת מיד : ‏`q1 = d`
    כותבת את `d`, ‏`q2 = q1` קוראת את ה-`q1` שנכתב הרגע, וכך גם `q3 = q2`. שלוש השורות הן בעצם
    `q1 = q2 = q3 = d`.

    השמה לא חוסמת, `<=`, עובדת בשני שלבים. בעלייה כל השורות קוראות את הצד הימני שלהן, כלומר את
    הערכים שלפני העלייה, והכתיבה לצד השמאלי נדחית לסוף צעד הזמן, אחרי שכל הבלוקים של העלייה רצו
    (אזור ה-NBA). כך `q2` מקבל את ה-`q1` הישן ו-`q3` את ה-`q2` הישן : שלושה רגיסטרים בשרשרת,
    כמו בחומרה.

    המילה `always_ff` לא מגינה מזה : השפה מרשה `=` בתוכו. Verilator שותק בהרצה רגילה, ורק עם
    `-Wall` הוא מזהיר, באזהרת סגנון, על כל אחת משלוש השורות. האזהרה על הראשונה :

    ```text title="verilator --lint-only -Wall delay3.sv"
    %Warning-BLKSEQ: delay3.sv:9:8: Blocking assignment '=' in sequential logic process
                                  : ... note: In instance 'delay3'
                                  : ... Suggest using delayed assignment '<='
    ```

    גם הסינתזה לא מצילה את הכוונה : ‏`q1` ו-`q2` נקראים רק אחרי שנכתבו באותה עלייה, ולכן אין
    צורך לזכור אותם, ונשאר פליפ-פלופ אחד, מ-`d` אל `q3`.

    #### השלבים { .sol-steps }

    <div class="steps" markdown>

    1. **מה הגל מראה :** ‏`q3` גבוה במחזורים 2, 3 ו-5, במקום 4, 5 ו-7. זו הצורה של `d`, מוזזת
       במחזור אחד ולא בשלושה.
    2. **הרמז בגל :** שלושת הרגיסטרים זהים בכל מחזור, ובשרשרת אמיתית `q2` מאחר אחרי `q1`.
    3. **השורות האשמות :** ‏`q2 = q1` ו-`q3 = q2` קוראות ערך שנכתב באותה עלייה, כי `=` כותבת
       מיד.
    4. **התיקון והבדיקה :** ‏`<=` בשלוש השורות. הבדיקה מריצה 400 מחזורים אקראיים, ובכל אחד
       ‏`q3` הוא `d` של שלושה מחזורים קודם.

    </div>

    #### הקוד { .sol-code }

    === "Python"
        ```python title="delay3"
        def delay3(d, blocking=False):
            """q1, q2, q3 during every cycle, for d of cycles 0, 1, 2, ..."""
            q1 = q2 = q3 = 0                  # (1)!
            trace = []
            for x in d:
                trace.append((q1, q2, q3))
                if blocking:                  # =: each line reads what the line above wrote
                    q1 = x
                    q2 = q1
                    q3 = q2
                else:                         # <=: every right-hand side is read first
                    q1, q2, q3 = x, q1, q2    # (2)!
            return trace
        ```

        1. כמו ב-Verilator : כל משתנה מתחיל ב-0.
        2. השמה מקבילה בפייתון קוראת את כל הצד הימני לפני שהיא כותבת משהו, בדיוק כמו `<=`.

    === "SystemVerilog"
        ```systemverilog title="delay3_fixed" hl_lines="9 10 11"
        module delay3_fixed (
          input  logic clk,
          input  logic d,
          output logic q3
        );
          logic q1, q2;

          always_ff @(posedge clk) begin
            q1 <= d;
            q2 <= q1;
            q3 <= q2;
          end
        endmodule
        ```

    #### למה זה נכון { .sol-proof }

    נעקוב אחרי העלייה שפותחת את מחזור 2. לפניה `d = 1` (הערך של מחזור 1), ו-`q1`, ‏`q2`, ‏`q3`
    הם 0. עם `=` : ‏`q1 = d` כותבת 1, ‏`q2 = q1` קוראת את ה-1 הזה, וגם `q3 = q2`. במחזור 2
    שלושתם 1, בדיוק כמו בגל. עם `<=` שלוש השורות קוראות קודם `d = 1`, ‏`q1 = 0` ו-`q2 = 0`,
    ורק אחר כך כותבות, ולכן במחזור 2 ‏`q1` הוא 1, ו-`q2` ו-`q3` עדיין 0.

    הטבלה, מחזור אחרי מחזור (מודגש : ‏`q3` שונה ממה שהמתכנן רצה) :

    <!-- gen 3 -->

    | מחזור | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
    |:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
    | ‏`d` | 0 | 1 | 1 | 0 | 1 | 0 | 0 | 0 |
    | הבאג, ‏`q1` | 0 | 0 | 1 | 1 | 0 | 1 | 0 | 0 |
    | הבאג, ‏`q2` | 0 | 0 | 1 | 1 | 0 | 1 | 0 | 0 |
    | הבאג, ‏`q3` | 0 | 0 | **1** | **1** | **0** | 1 | 0 | **0** |
    | התיקון, ‏`q1` | 0 | 0 | 1 | 1 | 0 | 1 | 0 | 0 |
    | התיקון, ‏`q2` | 0 | 0 | 0 | 1 | 1 | 0 | 1 | 0 |
    | התיקון, ‏`q3` | 0 | 0 | 0 | 0 | 1 | 1 | 0 | 1 |

    <!-- /gen -->

    עם `<=` כל עלייה מזיזה את השרשרת בצעד אחד : ‏`q1` מקבל את `d` של המחזור הקודם, ‏`q2` את
    ה-`q1` הקודם ו-`q3` את ה-`q2` הקודם. באינדוקציה על המחזורים, מכל מחזור \( k \ge 3 \) ‏`q3`
    הוא `d` של מחזור \( k - 3 \), ובמחזורים 0 עד 2 הוא עדיין 0, ערך ההתחלה. צורת הגל אחרי
    התיקון :

    ```wavedrom

      { name: "cycle", wave: "========", data: ["0", "1", "2", "3", "4", "5", "6", "7"] },
      { name: "d",     wave: "01.010.." },
      { name: "q1",    wave: "0.1.010." },
      { name: "q2",    wave: "0..1.010" },
    ```

### סעיף ב – מוצא עם אפשור

המוצא `y` צריך להיות `d` כש-`en` גבוה, ו-0 כש-`en` נמוך. זו לוגיקה צירופית, בלי שעון :

```systemverilog title="en_gate.sv" linenums="1"
module en_gate (
  input  logic       en,
  input  logic [3:0] d,
  output logic [3:0] y
);
  always_comb
    if (en) y = d;
endmodule
```

בסימולציה :

<!-- gen 1 -->

```wavedrom
{ signal: [
  { name: "clk",   wave: "p......." },
  { name: "cycle", wave: "========", data: ["0", "1", "2", "3", "4", "5", "6", "7"] },
  { name: "en",    wave: "01.0.10." },
  { name: "d",     wave: "========", data: ["3", "5", "9", "12", "7", "6", "10", "1"] },
  { name: "y",     wave: "===..=..", data: ["0", "5", "9", "6"] }
]}
```

<!-- /gen -->

עד מחזור 2 הכול נכון. במחזורים 3 ו-4 ‏`en` נמוך, אבל `y` נשאר 9 במקום 0, ובמחזורים 6 ו-7 הוא
נשאר 6. מה הבאג? הסבירו כל מחזור בגל.

??? tip "רמז 1"
    מה הבלוק כותב ל-`y` בריצה שבה `en` נמוך?

??? tip "רמז 2"
    אם אף שורה לא כותבת ל-`y`, מאיפה בא הערך שהוא מראה? איזה רכיב בחומרה מתנהג כך?

??? success "פתרון סעיף ב"
    !!! answer "תשובה בקצרה"
        כש-`en` נמוך אף שורה לא כותבת ל-`y`, והוא שומר את הערך האחרון : זה latch, לא לוגיקה
        צירופית. לכן `y` נשאר 9 ממחזור 2, ו-6 ממחזור 5. התיקון : ערך ברירת מחדל בראש הבלוק,
        ‏`y = '0;` לפני ה-`if` (או `else y = '0;`).

    #### הרעיון { .sol-idea }

    המילה `always_comb` מבטיחה שהבלוק רץ בכל פעם שאחת הכניסות שלו משתנה. היא לא מבטיחה שהבלוק
    כותב ל-`y` בכל ריצה. בריצה שבה `en` נמוך ה-`if` לא מתקיים, ו-`y` פשוט לא נכתב, ומשתנה
    ב-SystemVerilog שומר את הערך האחרון שנכתב בו. כדי לממש את זה בחומרה צריך רכיב זיכרון שפתוח
    כש-`en` גבוה ונעול כשהוא נמוך, כלומר latch. כאן Verilator כן מזהיר, גם בלי `-Wall` :

    ```text title="verilator --lint-only en_gate.sv"
    %Warning-LATCH: en_gate.sv:6:3: Latch inferred for signal 'y' (not all control paths of combinational always assign a value)
                                  : ... Suggest use of always_latch for intentional latches
    ```

    התיקון הוא לתת ל-`y` ערך בכל מסלול. הדרך הבטוחה היא השמה של ברירת מחדל בשורה הראשונה של
    הבלוק : כל ענף שבא אחריה יכול לדרוס אותה, וענף שלא כותב משאיר את ברירת המחדל, לא ערך ישן.

    #### השלבים { .sol-steps }

    <div class="steps" markdown>

    1. **מה הגל מראה :** ‏`y` שגוי במחזורים 3, 4, 6 ו-7. בכל אחד מהם `en` נמוך, ו-`y` מראה את
       `d` של המחזור האחרון שבו `en` היה גבוה.
    2. **הסיבה :** אין בבלוק שורה שכותבת ל-`y` כש-`en` נמוך, ולכן הוא שומר ערך : latch.
    3. **מה lint אומר :** אזהרת LATCH, כבר בהרצה רגילה.
    4. **התיקון והבדיקה :** ‏`y = '0;` בראש הבלוק. הבדיקה מריצה 400 מחזורים אקראיים, ובכל אחד
       ‏`y` הוא `d` כש-`en` גבוה ו-0 כשהוא נמוך.

    </div>

    #### הקוד { .sol-code }

    === "Python"
        ```python title="en_gate"
        def en_gate(en, d, default=True):
            """y during every cycle, for en and d of cycles 0, 1, 2, ..."""
            y = 0
            trace = []
            for e, x in zip(en, d):
                if default:
                    y = 0           # (1)!
                if e:
                    y = x
                trace.append(y)     # (2)!
            return trace
        ```

        1. התיקון : ‏`y` מקבל ערך בכל מחזור, לפני ה-`if`.
        2. בלי השורה של ברירת המחדל, מחזור עם `en` נמוך לא נוגע ב-`y`, והוא נשאר עם הערך
           הקודם : זה ה-latch.

    === "SystemVerilog"
        ```systemverilog title="en_gate_fixed" hl_lines="7"
        module en_gate_fixed (
          input  logic       en,
          input  logic [3:0] d,
          output logic [3:0] y
        );
          always_comb begin
            y = '0;
            if (en) y = d;
          end
        endmodule
        ```

    #### למה זה נכון { .sol-proof }

    נעבור על הגל של הקוד המקורי. במחזור 0 ‏`en` נמוך ו-`y` לא נכתב : הוא 0 רק כי Verilator מתחיל
    ב-0. במחזורים 1 ו-2 ‏`en` גבוה, ו-`y` הוא `d` : קודם 5, ואז 9. במחזור 3 ‏`en` יורד, הבלוק
    רץ כי `en` השתנה, לא כותב כלום, ו-`y` נשאר 9. במחזור 4 ‏`d` משתנה ל-7, הבלוק רץ שוב ושוב לא
    כותב, ו-`y` עדיין 9. במחזור 5 ‏`en` עולה ו-`y` הוא 6, ובמחזורים 6 ו-7 הוא נשאר 6.

    הטבלה, מחזור אחרי מחזור (מודגש : ‏`y` שונה ממה שהמתכנן רצה) :

    <!-- gen 5 -->

    | מחזור | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
    |:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
    | ‏`en` | 0 | 1 | 1 | 0 | 0 | 1 | 0 | 0 |
    | ‏`d` | 3 | 5 | 9 | 12 | 7 | 6 | 10 | 1 |
    | הבאג, ‏`y` | 0 | 5 | 9 | **9** | **9** | 6 | **6** | **6** |
    | התיקון, ‏`y` | 0 | 5 | 9 | 0 | 0 | 6 | 0 | 0 |

    <!-- /gen -->

    בתיקון השורה הראשונה כותבת 0 בכל ריצה של הבלוק, וה-`if` דורס אותה רק כש-`en` גבוה. כך `y`
    תלוי רק ב-`en` וב-`d` של אותו רגע, אין מה לזכור, והסינתזה נותנת AND של `en` עם כל ביט של
    `d`, בלי latch. צורת הגל אחרי התיקון :

    ```wavedrom

      { name: "clk",   wave: "p......." },
      { name: "cycle", wave: "========", data: ["0", "1", "2", "3", "4", "5", "6", "7"] },
      { name: "en",    wave: "01.0.10." },
    ```

### סעיף ג – ממוצע של שני בתים

המוצא `avg` צריך להיות הממוצע של שני מספרים בני 8 ביטים בלי סימן, מעוגל למטה :
\( \lfloor (a + b) / 2 \rfloor \). התוצאה תמיד נכנסת ב-8 ביטים.

```systemverilog title="avg8.sv" linenums="1"
module avg8 (
```

??? tip "רמז 1"
    כמה ביטים צריך כדי לכתוב את 300?

??? tip "רמז 2"
    ב-SystemVerilog הרוחב שבו מחושב ביטוי נקבע לפי האופרנדים שלו ולפי הצד השמאלי של ההשמה. מה

??? success "פתרון סעיף ג"
    !!! answer "תשובה בקצרה"
        הסכום `a + b` מחושב ב-8 ביטים, הרוחב הגדול מבין `a`, ‏`b` ו-`avg`. ‏300 לא נכנס ב-8
        ביטים : הנשא, ששווה 256, הולך לאיבוד, נשאר \( 300 - 256 = 44 \), ו-`44 >> 1` הוא 22.
        בכל זוג שבו \( a + b \ge 256 \) התוצאה קטנה ב-128 בדיוק. התיקון : להרחיב אופרנד לפני
        החיבור, ‏`8'(({1'b0, a} + b) >> 1)`.

    #### הרעיון { .sol-idea }

    ב-SystemVerilog רוחב החישוב של ביטוי אריתמטי נקבע מההקשר (context-determined) : הוא הרוחב
    הגדול מבין האופרנדים של הביטוי והצד השמאלי של ההשמה. כאן `a`, ‏`b` ו-`avg` כולם בני 8
    ביטים, ולכן גם `a + b` מחושב ב-8 ביטים, והנשא נזרק עוד לפני ההזזה. מספר ההזזה, ה-1 של
    `>> 1`, נקבע לבד (self-determined) ולא משתתף ברוחב, ולכן הוא לא מרחיב את החישוב אף שהוא
    מספר בן 32 ביטים.

    הקוד הזה עובר את `verilator --lint-only -Wall` בלי אזהרה אחת : כל הרוחבות שווים, ואין מה
    לחתוך. זה מה שהופך את הבאג למסוכן : הקוד נראה נכון, ה-lint שקט, והתוצאה נכונה בכל זוג שבו
    הסכום קטן מ-256.

    התיקון הוא להרחיב את החישוב ל-9 ביטים. ‏`{1'b0, a}` הוא אופרנד בן 9 ביטים, ולכן כל הביטוי
    מחושב ב-9 ביטים, והנשא נשמר עד ההזזה. ‏`8'(...)` מחזיר את התוצאה ל-8 ביטים במפורש. בלי ה-cast
    התוצאה עדיין נכונה, אבל Verilator מזהיר, גם בלי `-Wall`, שביטוי בן 9 ביטים נכנס ל-8 :

    ```text title="verilator --lint-only avg8_fixed.sv (without the cast)"
    %Warning-WIDTHTRUNC: avg8_fixed.sv:6:14: Operator ASSIGNW expects 8 bits on the Assign RHS, but Assign RHS's SHIFTR generates 9 bits.
    ```

    גם משתנה ביניים בן 9 ביטים עובד : ב-`logic [8:0] sum; assign sum = a + b;` הצד השמאלי בן 9
    ביטים, ולכן ההקשר הוא 9 ביטים ו-`a + b` מחושב עם הנשא. ‏`sum[8:1]` הם 8 הביטים העליונים, כלומר
    `sum >> 1`. בקוד המקורי הצד השמאלי, `avg`, בן 8 ביטים, ולכן הוא לא מרחיב כלום.

    #### השלבים { .sol-steps }

    <div class="steps" markdown>

    1. **מה הגל מראה :** במחזורים 2, 4, 5 ו-6 ‏`avg` קטן ב-128 בדיוק מהממוצע הנכון, ובשאר
       המחזורים הוא נכון.
    2. **החשבון :** הנשא של `a + b` שווה 256, ואחרי ההזזה 128. לכן כל זוג שבו \( a + b \ge 256 \)
       מאבד 128 בדיוק. במחזור 3 הסכום 255, אין נשא, והתוצאה נכונה.
    3. **החוק :** רוחב ההקשר הוא 8 ביטים, ו-`>> 1` לא מרחיב אותו.
    4. **התיקון והבדיקה :** ‏`{1'b0, a}` מרחיב את החישוב ל-9 ביטים. הבדיקה עוברת על כל 65,536
       הזוגות.

    </div>

    #### הקוד { .sol-code }

    === "Python"
        ```python title="avg8"
        def avg8(a, b, width=9):
            """(a + b) >> 1 computed in `width` bits, the result kept to 8 bits."""
            total = (a + b) % (1 << width)    # (1)!
            return (total >> 1) % 256
        ```

        1. ‏`width=8` הוא הקוד המקורי : הסכום נחתך ל-8 ביטים לפני ההזזה. ‏`width=9` הוא התיקון.

    === "SystemVerilog"
        ```systemverilog title="avg8_fixed" hl_lines="6"
        module avg8_fixed (
          input  logic [7:0] a,
          input  logic [7:0] b,
          output logic [7:0] avg
        );
          assign avg = 8'(({1'b0, a} + b) >> 1);   // (1)!
        endmodule
        ```

        1. ‏`{1'b0, a}` בן 9 ביטים, ולכן החיבור מחושב ב-9 ביטים. ‏`8'(...)` מחזיר ל-8 ביטים
           במפורש, בלי אזהרה.

    מהסכום האמיתי, ואחרי ההזזה התוצאה קטנה ב-128 בדיוק, כי הביט שההזזה זורקת זהה בשניהם. הבדיקה
    עוברת על כל 65,536 הזוגות : התיקון נכון בכולם, והקוד המקורי שגוי ב-32,640 זוגות, בדיוק אלה
    שבהם \( a + b \ge 256 \), ובכל אחד מהם ב-128. צורת הגל אחרי התיקון :

## נקודות חשובות ושאלות המשך

??? trap "מלכודת : לסדר את השורות מהסוף"
    אפשר "לתקן" את סעיף א בלי `<=`, אם כותבים את השורות מהסוף :

    ```systemverilog title="delay3, reversed"
    // reversed: the last stage first, so each line reads a value not yet written
    always_ff @(posedge clk) begin
      q3 = q2;
      q2 = q1;
      q1 = d;
    end
    ```

    כל שורה קוראת ערך שעוד לא נכתב בעלייה הזו, וזה עובד : הבדיקה מראה ש-`q3` הוא `d` של שלושה
    מחזורים קודם. אבל עכשיו הנכונות תלויה בסדר השורות. מי שמוסיף שלב, מזיז שורה או מפצל את
    הבלוק לשניים שובר אותה בלי אזהרה, חוץ מ-BLKSEQ של `-Wall`. עם `<=` הסדר לא משנה.

??? trap "מלכודת : החלפה בשני תהליכים"
    שני בלוקים באותה עלייה, וכל אחד קורא את מה שהשני כותב :

    ```systemverilog title="swap"
    // two processes at one edge: a takes b, b takes a
    always_ff @(posedge clk) a = b;
    always_ff @(posedge clk) b = a;
    ```

    בחומרה אלה שני פליפ-פלופים, והם מתחלפים. בסימולציה שני הבלוקים רצים באותו צעד זמן, בסדר
    שהשפה לא קובעת : הראשון כותב מיד, והשני כבר קורא את הערך החדש. אחרי העלייה `a` ו-`b` שווים,
    ואיזה משני הערכים נשאר תלוי בסדר שהסימולטור בחר. זה race. עם `<=` שני הבלוקים קוראים לפני
    שמישהו כותב, והם מתחלפים בכל סימולטור, כמו בחומרה.

??? trap "מלכודת : חילוק ב-2 עובד, הזזה ב-1 לא"
    הביטוי `(a + b) / 2` נותן 150 עבור 200 ו-100, בלי אזהרה : ה-2 הוא מספר בן 32 ביטים, והוא
    אופרנד של החילוק, ולכן ההקשר הוא 32 ביטים והנשא נשמר. זה עובד במקרה, מסיבה שלא כתובה בקוד :
    מי שיכתוב `8'd2` במקום 2 יחזיר את הבאג, ויקבל שוב 22. עדיף להרחיב במפורש, כמו בתיקון.

??? trap "מלכודת : Verilator מתחיל ב-0"
    ‏Verilator הוא סימולטור של שני מצבים, ובהגדרות ברירת המחדל כל משתנה מתחיל ב-0. לכן במחזור
    0 של סעיף ב ‏`y` נראה נכון, ו-`q1`, ‏`q2` ו-`q3` של סעיף א מתחילים נקיים. בסימולטור של ארבעה
    מצבים אותם אותות היו X עד הכתיבה הראשונה, ו-X על המוצא של סעיף ב היה מסגיר את ה-latch כבר
    במחזור 0. ובסיליקון, רגיסטר בלי איפוס מתחיל בערך כלשהו, לא ב-0.

??? followup "שאלות המשך"
    - **הכלל :** מתי כותבים `=` ומתי `<=`?

        ??? fu-answer "תשובה"
            בבלוק מתוזמן (`always_ff`) ‏`<=`, ובבלוק צירופי (`always_comb`) ‏`=`, ולא מערבבים
            באותו בלוק. כך הסימולציה מתנהגת כמו החומרה, בלי תלות בסדר השורות או בסדר הבלוקים.

    - **‏`case` בלי `default` :** מה קורה כש-`case` בתוך `always_comb` לא מכסה את כל הערכים ואין
      ענף `default`?

        ??? fu-answer "תשובה"
            אותו latch : בערך שאין לו ענף המוצא לא נכתב, ושומר את הערך הקודם. Verilator מזהיר
            CASEINCOMPLETE, עם דוגמה לערך חסר, וגם LATCH. התיקון זהה : ברירת מחדל לפני ה-`case`,
            או ענף `default`.

    - **‏`unique` ו-`priority` :** מה `unique case` ו-`priority case` מבטיחים, ומה לא?

        ??? fu-answer "תשובה"
            הם אומרים שאף ערך לא נשאר בלי ענף (‏`unique` גם שאין שני ענפים מתאימים), והסימולציה
            מדווחת על הפרה. הסינתזה מניחה שזה נכון ולא בונה latch. אבל הם לא נותנים ל-`y` ערך,
            ואם ערך כזה בכל זאת מגיע, הסימולציה והחומרה כבר לא מסכימות. עדיף ברירת מחדל מפורשת.

    - **למה latch רע בחומרה?** האם זו רק הפתעה בסימולציה?

        ??? fu-answer "תשובה"
            לא. latch שקוף כל זמן ש-`en` גבוה, ולכן ניתוח התזמון צריך לעקוב אחרי מסלולים שעוברים
            דרכו, ותקלה (glitch) על ה-`en`, שבא מלוגיקה צירופית, נכנסת ישר לנתונים. בבדיקות ייצור
            (DFT) קשה להכניס אותו לשרשרת הסריקה כמו פליפ-פלופ. לכן latch שלא תוכנן הוא באג.

    - **‏signed מול unsigned :** ‏`logic signed [7:0] s = -1;` ו-`logic [7:0] n = 5;`. האם `s < n`?

        ??? fu-answer "תשובה"
            לא. כשאחד האופרנדים בלי סימן, כל ההשוואה בלי סימן : ‏`s` נקרא כ-255, ו-255 לא קטן
            מ-5. כך גם `int i = -1;` : ‏`i < n` שקר. לעומת זאת `s < 5` נכון, כי 5 הוא `int` עם
            סימן, וגם `i < int'(n)` נכון.

    - **‏`a + b` בהדפסה ובתנאי :** עם `a = 200` ו-`b = 100` בני 8 ביטים, מה מדפיס
      `$display("%0d", a + b)`, ומה נותנים `a + b > 255` ו-`a + b > 8'd255`?

        ??? fu-answer "תשובה"
            ההדפסה נותנת 44 : הרוחב של ארגומנט של `$display` נקבע לבד, 8 ביטים. ‏`a + b > 255`
            נכון, כי ה-255 בן 32 ביטים ומרחיב את החיבור. ‏`a + b > 8'd255` לעולם לא נכון : הכול
            ב-8 ביטים, ו-Verilator מזהיר CMPCONST, ‏"Comparison is constant due to limited range".

    - **מה lint תופס :** אילו משלושת הבאגים Verilator מוצא, ובאיזו הגדרה?

        ??? fu-answer "תשובה"
            את ה-latch של סעיף ב, באזהרת LATCH, גם בלי `-Wall`. את ה-`=` של סעיף א, ב-BLKSEQ, רק עם
            `-Wall`. את הנשא של סעיף ג לא, כי כל הרוחבות שווים. לכן את סעיף ג תופסים רק בבדיקה, למשל
            על כל הזוגות או על ערכי קצה כמו 255 ועוד 1.
