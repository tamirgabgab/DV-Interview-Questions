## השאלה

בין שני בלוקים יש לחיצת ידיים פשוטה: המבקש מרים `req`, והמשיב עונה ב-`ack` למשך מחזור
אחד. חוזה הממשק, בשעון `clk` עם איפוס `rst_n`:

1. **‏`req` מחזיק:** מרגע ש-`req` עלה הוא נשאר גבוה עד המחזור שבו מגיע `ack` (כולל).
2. **‏`ack` בזמן:** ‏`ack` מגיע בין מחזור אחד לשלושה מחזורים אחרי העלייה של `req`.
3. **אין `ack` יתום:** ‏`ack` לא מופיע כש-`req` נמוך.
4. **עסקה אחת לכל `req`:** במחזור שאחרי `ack` ה-`req` יורד (עסקה חדשה מתחילה בעלייה
   חדשה).

### סעיף א – כתבו את ה-assertions

כתבו ארבע concurrent assertions ב-SystemVerilog, אחת לכל חוק, בתוך מודול בודק שמקבל
את `clk`, `rst_n`, `req` ו-`ack`. הסבירו את הבחירה בין `|->` ל-`|=>`, מה עושה
`##[1:3]`, ומה `disable iff` נותן.

### סעיף ב – ציירו ובדקו

ציירו דיאגרמת תזמון של עסקה תקינה ושל שלוש הפרות (‏`ack` מאוחר, ‏`req` שנופל לפני
`ack`, ‏`ack` יתום), וכתבו מודל ייחוס (ב-Python או בטסטבנץ') שעובר על רצף דגימות ומוצא
את אותן הפרות, כדי לבדוק את ה-assertions עצמן.

??? interviewer "מה המראיין בודק"
    - **סמנטיקה של SVA:** דגימה בשפת השעון, ההבדל בין implication חופפת ללא-חופפת, ומה
      "fails" אומר על property עם חלון זמן.
    - **תרגום חוזה לתכונות:** האם כל חוק הופך ל-property אחת ברורה, בלי לערבב חוקים
      ובלי assertions שתמיד עוברות.
    - **‏`disable iff` ואיפוס:** מה קורה ל-property שבאמצע חלון כשמגיע reset.
    - **אימות של ה-assertions:** assertion שאף פעם לא נכשל הוא חשוד. האם המועמד יודע
      להזריק הפרות ולצפות לכישלון, ואיך סופרים הפרות כדי להשוות למודל ייחוס.
    - **מה לא לבדוק:** חוק 2 לא אומר "‏`ack` מגיע בדיוק אחרי 3 מחזורים", וחוק 3 לא אומר
      "‏`req` גורר `ack`". מועמד טוב נזהר לא להמציא חוקים.

??? tip "רמז 1"
    כל חוק הוא "אם קרה X, אז Y": X הוא האנטצדנט (לפני החץ), Y הקונסקוונט. השאלה
    היחידה היא **מתי** Y: באותו מחזור (‏`|->`), במחזור הבא (‏`|=>`) או בחלון (‏`##[m:n]`).

??? tip "רמז 2"
    חוק 1 הוא קל יותר לכתוב כצעד אחד: "אם `req` גבוה ועדיין אין `ack`, במחזור הבא
    `req` עדיין גבוה". זה אותו דבר כמו "מחזיק עד ה-ack", בלי `throughout` ובלי
    חזרות.

??? success "פתרון סעיף א"
    !!! answer "תשובה בקצרה"
        ארבע properties בשעון `posedge clk`, כולן עם `disable iff (!rst_n)`:
        ‏`(req && !ack) |=> req` (חוק 1), ‏`$rose(req) |-> ##[1:3] ack` (חוק 2),
        ‏`ack |-> req` (חוק 3), ‏`ack |=> !req` (חוק 4). ‏`|->` כשהתוצאה נבדקת באותו
        מחזור של התנאי, ‏`|=>` כשהיא נבדקת מהמחזור הבא, ו-`##[1:3]` פותח חלון של שלושה
        מחזורים שבו מספיק שה-`ack` יופיע פעם אחת.

    #### הרעיון { .sol-idea }

    ‏SVA דוגם את כל האותות בשפת השעון ובודק **תכונה** על רצף הדגימות. כל חוק של החוזה
    הוא implication: אנטצדנט שמתאים לדגימה (או לרצף), וקונסקוונט שחייב להתקיים ביחס
    אליה בזמן. ‏`a |-> b` בודק את `b` באותה שפה שבה `a` התאים; ‏`a |=> b` בשפה הבאה;
    ‏`a |-> ##[1:3] b` מרוצה אם `b` נכון באחת משלוש השפות הבאות. ‏`disable iff (!rst_n)`
    מבטל כל ניסיון שבאמצעו הגיע reset, כדי שחלון פתוח לא ייכשל בגלל האיפוס.

    #### השלבים { .sol-steps }

    <div class="steps" markdown>

    1. **חוק 1 כצעד:** "מחזיק עד `ack`" שקול ל-"בכל מחזור שבו `req` גבוה בלי `ack`, במחזור
       הבא `req` עדיין גבוה": `(req && !ack) |=> req`. הפרה נספרת במחזור שבו `req` נפל.
    2. **חוק 2 כחלון:** האירוע הוא העלייה, `$rose(req)` (נמוך בדגימה הקודמת, גבוה
       בזו). מהעלייה, `##[1:3] ack`: ‏`ack` באחת משלוש השפות הבאות. ה-property נכשלת
       רק אחרי השפה השלישית בלי `ack`, ולכן הכישלון מדווח שלושה מחזורים אחרי העלייה.
    3. **חוק 3 חופף:** ‏`ack |-> req`: באותה דגימה שבה `ack` גבוה, גם `req` גבוה. אין
       כאן זמן, ולכן `|->` ולא `|=>`.
    4. **חוק 4 לא חופף:** ‏`ack |=> !req`: בשפה שאחרי `ack` ה-`req` כבר נמוך. בחוק הזה
       `|->` היה שגוי, כי באותה שפה של `ack` ה-`req` חייב להיות גבוה (חוק 3).
    5. **ספירה:** כל assertion מקבלת action block של `else` שסופר ומדפיס, כדי שהטסטבנץ'
       יוכל להשוות את מספר הכישלונות למודל הייחוס במקום לעצור בכישלון הראשון.

    </div>

    #### הקוד { .sol-code }

    המודול הבודק (checker) מצורף לממשק; `fails` הוא סך ההפרות, לכל חוק מונה משלו.
    מודל הייחוס ב-Python עובר על אותן דגימות ומחזיר את המחזורים של כל הפרה.

    === "SystemVerilog"
        ```systemverilog title="module handshake_checker" linenums="1" hl_lines="13 16 19 22"
        module handshake_checker #(int MAX_WAIT = 3) (
          input  logic clk,
          input  logic rst_n,
          input  logic req,
          input  logic ack,
          output int   fails
        );
          int fail_hold = 0, fail_late = 0, fail_orphan = 0, fail_drop = 0;
          assign fails = fail_hold + fail_late + fail_orphan + fail_drop;

          // 1. once req is high without ack, it is still high next cycle
          a_req_holds: assert property (@(posedge clk) disable iff (!rst_n)
            (req && !ack) |=> req)                                    // (1)!
            else begin fail_hold++; $display("%0t req dropped before ack", $time); end

          // 2. ack within 1..MAX_WAIT cycles after req rises
          a_ack_in_time: assert property (@(posedge clk) disable iff (!rst_n)
            $rose(req) |-> ##[1:MAX_WAIT] ack)                        // (2)!
            else begin fail_late++; $display("%0t ack too late", $time); end

          // 3. no ack without a request
          a_no_orphan_ack: assert property (@(posedge clk) disable iff (!rst_n)
            ack |-> req)                                              // (3)!
            else begin fail_orphan++; $display("%0t ack without req", $time); end

          // 4. the cycle after ack, req is low (one transaction per req pulse)
          a_req_drops: assert property (@(posedge clk) disable iff (!rst_n)
            ack |=> !req)                                             // (4)!
            else begin fail_drop++; $display("%0t req held after ack", $time); end
        endmodule
        ```

        1. ‏Implication לא חופפת: האנטצדנט בדגימה הזו, הקונסקוונט בדגימה הבאה. אם
           `req` ירד לפני `ack`, האנטצדנט התאים במחזור האחרון שבו הוא היה גבוה והקונסקוונט
           נכשל במחזור שאחריו.
        2. ‏`$rose(req)` משווה לדגימה הקודמת. ‏`##[1:MAX_WAIT] ack` הוא חלון: מספיק
           `ack` אחד בתוכו, והכישלון מדווח רק כשהחלון נסגר בלי `ack`.
        3. ‏Implication חופפת: שני האותות באותה דגימה.
        4. במחזור שאחרי `ack` ה-`req` נמוך. עם `|->` זה היה סותר את חוק 3.

    === "Python"
        ```python title="check_handshake" linenums="1" hl_lines="10 14 17 19"
        def check_handshake(req: list[int], ack: list[int], max_wait: int = 3) -> dict[str, list[int]]:
            """The four rules on sampled values (index = clock cycle). Returns the cycles at
            which each rule is violated, the cycle at which the SVA reports the failure."""
            n = len(req)
            fails = {"hold": [], "late": [], "orphan": [], "drop": []}
            for t in range(n):
                prev_req = req[t - 1] if t else 0
                prev_ack = ack[t - 1] if t else 0
                if t and prev_req and not prev_ack and not req[t]:
                    fails["hold"].append(t)                           # (1)!
                if req[t] and not prev_req:                           # $rose(req)
                    window = ack[t + 1:t + 1 + max_wait]
                    if len(window) == max_wait and not any(window):
                        fails["late"].append(t + max_wait)            # (2)!
                if ack[t] and not req[t]:
                    fails["orphan"].append(t)                         # (3)!
                if t and prev_ack and req[t]:
                    fails["drop"].append(t)                           # (4)!
            return fails
        ```

        1. ‏`req` היה גבוה בלי `ack` ונפל: ההפרה נרשמת במחזור הנפילה, כמו `|=>`.
        2. אין `ack` באף אחד משלושת המחזורים שאחרי העלייה: ההפרה נרשמת בסוף החלון. חלון
           שנחתך בסוף הרצף לא נספר, כמו property שעדיין פתוחה בסוף הסימולציה.
        3. ‏`ack` בלי `req` באותה דגימה.
        4. ‏`req` עדיין גבוה במחזור שאחרי `ack`.

    #### למה זה נכון { .sol-proof }

    **מה כל property באמת אומרת.** הרשימה שלמה ולא יתרה: חוק 1 מכסה כל מחזור של המתנה,
    חוק 2 את משך ההמתנה, חוק 3 את ה-`ack` הבודד, חוק 4 את הסיום. אין צורך ב-property
    "‏`req` גורר `ack`" כי חוק 2 כבר דורש אותו, ואין צורך ב-"‏`ack` מחזור אחד בלבד" כי
    `ack` שנמשך שני מחזורים מפר את חוק 4 (במחזור השני `req` עדיין גבוה לפי חוק 3) או
    את חוק 3.

    **למה `disable iff`.** property עם חלון שנפתח לפני reset הייתה נכשלת בזמן האיפוס
    (‏`req` ו-`ack` מתאפסים ואין `ack` בחלון). ‏`disable iff (!rst_n)` זורק כל ניסיון פתוח
    ברגע שהאיפוס פעיל, ומתחיל לבדוק מחדש רק אחרי השחרור.

    #### סיבוכיות { .sol-cost }

    בסימולציה: כל assertion מחזיקה לכל היותר כמה ניסיונות פתוחים בו-זמנית (חוק 2: עד
    שלושה, אחד לכל עלייה בחלון), זניח. בסינתזה ל-FPGA או לאמולטור, חוק 2 הוא מונה קטן
    לכל ניסיון פתוח; השאר הם שער אחד ופלופ אחד.

    ציירו קודם את העסקה התקינה, ואז שנו דבר אחד בכל פעם: אחרו את `ack`, הפילו את
    `req` מוקדם, הוסיפו `ack` בלי `req`.

??? success "פתרון סעיף ב"
    !!! answer "תשובה בקצרה"
        בעסקה תקינה `req` עולה, `ack` מגיע אחרי מחזור עד שלושה בעוד `req` גבוה, ו-`req`
        יורד מיד אחריו. בשלוש ההפרות נכשלת בדיוק property אחת: `ack` במחזור הרביעי מפר את
        חוק 2 (והכישלון מדווח שלושה מחזורים אחרי העלייה), `req` שנופל לפני `ack` מפר את
        חוק 1 (ואם ה-`ack` בכל זאת מגיע, גם את חוק 3), ו-`ack` בלי `req` מפר את חוק 3.
        מודל הייחוס מוצא את אותם מחזורים, והטסטבנץ' משווה את המונים.

    #### הרעיון { .sol-idea }

    בודקים assertions כמו שבודקים כל קוד: עם מקרים שאמורים לעבור ועם מקרים שאמורים
    להיכשל, וסופרים. מודל ייחוס פרוצדורלי קטן (עשרים שורות על רצף דגימות) נותן את
    מספר ההפרות הצפוי ואת המחזור של כל אחת, והטסטבנץ' מזריק הפרות אקראיות ודורש
    שוויון בין המונים של ה-checker למונים של המודל.

    #### השלבים { .sol-steps }

    <div class="steps" markdown>

    1. **עסקה תקינה:** `req` עולה במחזור 1, `ack` במחזור 3, `req` יורד במחזור 4. כל
       ארבע ה-properties מרוצות.
    2. **‏`ack` מאוחר:** `req` עולה במחזור 1, `ack` רק במחזור 5. חוק 2 נכשל במחזור 4,
       סוף החלון. חוקים 1, 3 ו-4 מרוצים (‏`req` מחזיק, ה-`ack` עם `req`, ו-`req` יורד
       אחריו).
    3. **‏`req` נופל:** `req` גבוה במחזורים 1 ו-2 ויורד במחזור 3 בלי `ack`. חוק 1 נכשל
       במחזור 3; חוק 2 נכשל במחזור 4 אם לא מגיע `ack` עד אז.
    4. **‏`ack` יתום:** `ack` במחזור 2 בלי `req`. חוק 3 נכשל במחזור 2.
    5. **הטסטבנץ':** מחולל אקראי שבדרך כלל מתנהג יפה (‏`ack` אחרי 1 עד 3 מחזורים) ומדי
       פעם מזריק אחת משלוש ההפרות; מודל הייחוס רץ על אותן דגימות; בסוף משווים ארבעה
       מונים.

    </div>

    #### למה זה נכון { .sol-proof }

    **עסקה תקינה.** ‏`ack` במחזור השלישי אחרי העלייה, בתוך החלון:

    ```wavedrom
    { signal: [
      { name: "clk",   wave: "p......." },
      { name: "req",   wave: "01..0..." },
      { name: "ack",   wave: "0..10..." },
      { name: "cycle", wave: "========", data: ["0", "1", "2", "3", "4", "5", "6", "7"] }
    ], head: { text: "ok: rose at 1, ack at 3, req low at 4" } }
    ```

    **שלוש הפרות.** מלמעלה למטה: `ack` מאוחר (חוק 2 נכשל במחזור 4), `req` שנופל (חוק 1
    נכשל במחזור 3, חוק 2 במחזור 4), `ack` יתום (חוק 3 נכשל במחזור 2):

    ```wavedrom
    { signal: [
      { name: "clk",      wave: "p......." },
      { name: "req",      wave: "01....0." },
      { name: "ack",      wave: "0....10." },
      { name: "fails",    wave: "0...10..", data: [""] },
      {},
      { name: "req",      wave: "01.0...." },
      { name: "ack",      wave: "0......." },
      { name: "fails",    wave: "0..1.0..", data: [""] },
      {},
      { name: "req",      wave: "0......." },
      { name: "ack",      wave: "0.10...." },
      { name: "fails",    wave: "0.10....", data: [""] }
    ], head: { text: "late ack / req dropped / orphan ack" } }
    ```

    **אותם מחזורים במודל הייחוס.** על הרצפים האלה `check_handshake` מחזיר
    `{"late": [4]}`, ‏`{"hold": [3], "late": [4]}` ו-`{"orphan": [2]}` (ושאר הרשימות ריקות),
    וזה בדיוק מה שהבדיקות של הדף בודקות. הטסטבנץ' מריץ את ה-checker עם `--assert` על
    400 עסקאות אקראיות עם הפרות מוזרקות, ומשווה את ארבעת המונים למודל הייחוס שכתוב בו
    פרוצדורלית.

    **לנסות בעצמכם.** בתיבה הבאה מציירים את `req` ואת `ack` משבצת אחרי משבצת, וארבע
    ה-assertions נבדקות בכל מחזור כמו במודל הייחוס: ✗ מסמן את המחזור שבו כל אחת מדווחת
    על כישלון. ארבע הדיאגרמות שלמעלה הן הכפתורים.

    #### סיבוכיות { .sol-cost }

    מודל הייחוס: מעבר אחד על הרצף, \( O(n \cdot \text{max\_wait}) \). הטסטבנץ': ככל
    שמזריקים יותר סוגי הפרות, כך הביטחון שה-assertions באמת בודקות את מה שחשבנו גדל;
    assertion שלא נכשלה אף פעם בכל הרגרסיה היא ממצא, לא הצלחה.

## נקודות חשובות ושאלות המשך

??? trap "מלכודת: `|->` במקום `|=>` בחוק 4"
    ‏`ack |-> !req` דורש ש-`req` יהיה נמוך **באותה** דגימה שבה `ack` גבוה, בסתירה
    לחוק 3. ה-assertion הייתה נכשלת בכל עסקה תקינה. ההבדל בין החצים הוא מחזור שלם, ובדף
    החוזה כתוב "במחזור שאחרי".

??? trap "מלכודת: חלון שנכשל בגלל reset"
    בלי `disable iff`, ‏`req` שעלה שני מחזורים לפני reset פותח חלון, האיפוס מוריד את
    `ack`, והחלון נסגר בלי `ack`: כישלון מדומה. כל property עם זמן צריכה `disable iff`
    על האיפוס (או `default disable iff` במודול).

??? trap "מלכודת: assertion שתמיד עוברת"
    ‏`req |-> ##[1:3] ack` (בלי `$rose`) נראית אותו דבר, אבל היא מתאימה **בכל** מחזור
    שבו `req` גבוה, ולכן גם בעסקה תקינה היא פותחת ניסיון במחזור של ה-`ack` עצמו, שדורש
    `ack` נוסף אחריו, ונכשלת. ולהפך, assertion עם אנטצדנט שאף פעם לא מתקיים עוברת
    תמיד ("vacuous pass"). בודקים גם כיסוי: `cover property` על האנטצדנט.

??? followup "שאלות המשך"
    - **‏`ack` באותו מחזור:** אם הממשק מתיר `ack` צירופי באותו מחזור של `req`, איך
      משתנים חוקים 2 ו-4? (‏`##[0:3]`, וחוק 4 הופך ל-`ack |=> !req` רק אם `req` לא עלה
      שוב.)
    - **עסקאות גב-אל-גב:** אם מותר ל-`req` להישאר גבוה אחרי `ack` ולהתחיל עסקה חדשה
      מיד, חוק 4 מתבטל ו-`$rose` כבר לא מזהה את העסקה השנייה. מה מחליף אותו?
    - **‏valid / ready:** ב-AXI-stream `valid` חייב להחזיק עד `ready`, אבל `ready` רשאי
      להופיע לפני `valid` ואין חלון זמן. אילו מארבעת החוקים נשארים?
    - **כיסוי:** כתבו `cover property` שמוודא שראינו `ack` אחרי 1, אחרי 2 ואחרי 3 מחזורים,
      כי assertion על חלון שתמיד נענה ב-1 לא בדקה את הגבול.
