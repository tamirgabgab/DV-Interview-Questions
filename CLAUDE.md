# CLAUDE.md — working rules for this repository

This is a Hebrew, right-to-left MkDocs Material site of Design Verification interview
questions, published to GitHub Pages from `main`. `README.md` has the links to the site and a
map of the repository; `CONTRIBUTING.md` documents the content format and the tooling. The
working notes are in `notes/`: `notes/CATALOG.md` lists the questions (written by
`tools/build/catalog.py`); `notes/HANDOFF.md` is the living task list and the recent work log
(older logs in `notes/HANDOFF-archive.md` and `notes/HANDOFF-archive-2.md`);
`notes/VIDEOS.md` is the plan of the tutorial videos (Manim, one per question, a chapter per
part). The tools are in `tools/checks/` (what CI runs), `tools/build/` (what the site is built
from), `tools/authoring/` (the new-question scaffold and its template) and `tools/figures/`.
Read `CONTRIBUTING.md` and `notes/HANDOFF.md` before a work session, and update
`notes/HANDOFF.md` (work log, open items) at the end of every session.

## Language and RTL

- Always answer the owner in Hebrew, never in English: every chat reply, status update,
  question and end-of-round summary, also after a model switch or a context summary.
  English appears only as relevant technical terms, identifiers and file names inside a
  Hebrew sentence. Question content is Hebrew. Code, comments, identifiers,
  commit messages, `README.md`, `CONTRIBUTING.md`, `notes/HANDOFF.md` and this file are English.
- Times shown to the owner are Israel time (Asia/Jerusalem: UTC+2 in winter time, which
  runs from 25 October 2026 to 26 March 2027, and UTC+3 in summer time), never UTC. Tools report UTC: convert
  before writing, e.g. "23:31 (שעון ישראל)".
- RTL safety: every paragraph, heading, list item and table cell starts with a Hebrew word.
  A line that must start with Latin text, inline code, a number followed by a period, or
  math gets the RLM mark (U+200F, `‏`) first. English terms go in the middle or at the end
  of a sentence.
- Colons in Hebrew text have a space on both sides: a non-breaking space (U+00A0) before,
  so the colon never wraps to the start of a line, and an ordinary space after ("סיבוב 8 :
  שלום", "**זמן :** ..."). This covers pages, admonition titles, figure generators, the
  explorer strings (`docs/javascripts/explorer/`) and the hook's HTML. It does not apply
  to times and ratios (12:00, 23:58:59), code, math, URLs or English-only text.
- No Hebrew inside MathJax (`\text{...}` renders reversed). In inline SVG, Hebrew `<text>`
  gets `direction="rtl"`; prefer an HTML legend over SVG text.
- No math in headings: the sidebar's table of contents and the search
  results show headings as plain text, so `\( L - 1 \)` appears raw there. Write the
  heading in words ("L − 1", "בזיכרון קבוע") and keep its old anchor with `{ #id }`.
- Long display math or inline chains widen the page on phones: split equations with
  `aligned`, write number chains as text in `<span dir="ltr">`.
- Numbers whose order is left to right must be isolated LTR in Hebrew text, table cells,
  figure legends and the explorers' strings: in a right-to-left line a space or ", "
  between numbers splits them into runs that the browser lays out from the right. Bits or
  digits written apart ("0 1" showed as "1 0" in 0055's state codes), rows of a matrix or
  an array ("1 1 1 1 0", 0046) and ordered tuples ("(3, 1)" read as (1, 3) in 0013) go in
  `<span dir="ltr">…</span>` (in a generator, a helper like `ltr_bits` in q0055.py), or
  are written without spaces ("01"), or in math or code. A cell that then starts with
  the span gets the RLM first. Plain lists read in order ("1, 2, 4, 8"), years and
  thousands separators ("1,000") need nothing. Before pushing a page with such
  numbers, look at the rendered line, not only the source.

## Question pages

- One Markdown file per question: `docs/questions/<level>/<id>-<slug>.md`, zero-padded id
  unique across the repository, `level` equal to the folder. Start from
  `tools/authoring/question.md`; the skeleton (interviewer block, hint ladder, short answer,
  solution blocks idea → steps → code → proof → cost, traps, follow-ups with a short
  collapsed answer each) is described in
  `CONTRIBUTING.md` and enforced by `python tools/checks/lint_pages.py`.
- Code answers in Python and SystemVerilog as linked tabs, Python first (the owner's choice,
  2026-10-29). The pages
  are the single source of truth: tests and the run panel execute the page code as is, so
  never change code on a page without running its tests. Annotation markers (`// (1)!`,
  `# (1)!`, or ` (1)` at the end of a comment) are the only decoration allowed on code
  lines.
- Figures are inline SVG generated by `tools/figures/q<id>.py`; the page copy must match
  the generator output (tests check it). New generators define `blocks()`, use
  `tools/figures/charts.py`, and their blocks sit between `<!-- gen n -->` markers that
  `python tools/figures/fill.py <id>` rewrites. Colours come from CSS variables in
  the stylesheets in `docs/stylesheets/` (the palette in `01-base.css`), never hard-coded.
- Start a question with `python tools/authoring/new_question.py` (see `CONTRIBUTING.md`). Interactive
  sliders are a `data-kind` with its own file in `docs/javascripts/explorer/` (the shared
  code is `core.js`), tested under Node. A box keeps its figures still while it steps
  (`check_jumps.py`): a block that grows with the steps goes under the figures, or is
  marked `data-steady` (see `CONTRIBUTING.md`).
- The owner's own code is kept as sent; comments may be added, and bugs are called out to
  the owner rather than silently fixed.
- A source file from the owner (a solution write-up with tables and formulas) is checked
  first: recompute every table, example and closed form in the question's test with exact
  arithmetic, try the edge cases of the general formula, and tell the owner what does not
  hold before writing the page (0026–0028 found a capped last person and one rounding).

## Tests and checks

```bash
python tools/checks/lint_pages.py            # page skeleton and RTL rules
python tools/checks/check_videos.py          # the video fields of the pages, the captions of videos/*/script.md
python tools/checks/run_tests.py             # pytest + Verilator (needs Verilator 5.052+ with z3)
mkdocs build --strict                 # the build CI runs
python tools/checks/check_links.py           # internal links and anchors of the built site
python tools/checks/check_phone.py           # every page at 390 px (add --local-cdn in a sandbox)
python tools/checks/check_explorers.py       # every explorer box: buttons clicked, link and saved state
python tools/checks/check_jumps.py           # every box stepped at 390 and 1200 px: no figure moves
python tools/checks/check_inputs.py          # every box field typed into: Enter, Tab and an input method apply it
python tools/checks/check_contrast.py        # the site's colour pairs, light and dark (WCAG 2)
python tools/checks/check_404.py             # the 404 page under the site's path, both widths
python tools/checks/check_keyboard.py        # a keyboard pass: tab order, focus rings, names, the components' keys
```

The linter checks RTL at every paragraph start (indented blocks and the steps timeline
included) and warns about literal SVG colours; the phone check also warns about display
math wider than its column (split it with `aligned`), and fails when the enlarge button of a
figure covers SVG text (reading-tools.js moves it above such a figure). In CI it also fails
on figure text under 9 px at 390 px and on serious axe findings (`--small-fail --axe-fail`). `--scheme dark` runs the phone check
in dark mode; CI runs it only on a manual run with `phone_dark`. Every page's line of the
phone check also gives its weight (HTML KB, bytes fetched, requests); over 400 KB of HTML is
a warning. Every page is also loaded with its text enlarged 1.3 times (a phone's text size), and
fails if it is then wider than the screen; at both sizes a box's slider and its value must
sit on one row. Node runs the explorer
tests (`docs/javascripts/*.js` against the Python reference).

All twelve run in CI on every push that touches the site (a push of only README, CONTRIBUTING,
this file or files under `notes/` runs nothing, and `main` skips the checks for a commit that
already passed on its branch); a failure blocks the deploy. A new colour pair (a text
or a mark on a fill) goes into the `PAIRS` list of `tools/checks/check_contrast.py`. Verilator
notes and simulator quirks are listed in `notes/HANDOFF.md` under "Technical notes".

## Design skills

- `.claude/skills/` holds third-party design skills (ui-ux-pro-max, impeccable,
  web-design-guidelines); `.claude/skills/README.md` lists their sources, licenses and how to
  run them here. Their advice never overrides the rules of this file (RTL, the palette
  variables, contrast, reduced motion, the checks); a conflict goes to the owner.

## Workflow

- Ask the owner guiding questions before a big change, then implement; end a work round
  with a short summary by sections.
- Develop on the designated work branch. Push to `main` (which publishes the site) only
  when the owner asks. Fast-forward `main` to the branch; do not rewrite history.
- Small, local fixes go to `main` without waiting for the branch CI (the owner's standing
  permission): a bug fix or a tweak in one place (one page, one box, one hook function,
  one config line), no new question and no change shared by many pages' layout. Run only
  the checks that cover the change, about five minutes in all: `lint_pages.py` and
  `run_tests.py` for the touched question, `mkdocs build --strict`, `check_links.py`, and
  `check_phone.py` / `check_explorers.py` with `--only` on the touched pages. Commit on
  the branch, fetch, and fast-forward `main` to it only if `main` is still its ancestor
  (another session may have moved it; then merge `main` first). The `main` CI still runs
  every check and blocks a broken deploy: if it fails, fix it on `main` at once. Anything
  bigger keeps the full flow: branch CI green first, then fast-forward `main`.
- Text-only changes to question pages (prose only: no code block, front matter, generated
  block or box changes; the owner, 2026-11-02) go straight to `main` after the
  fast checks: `lint_pages.py`, `run_tests.py --python-only <id>`, `mkdocs build --strict`,
  `check_links.py`, `check_phone.py --only <id>`, and a screenshot of the changed part
  looked at (display math, indentation inside lists and admonitions, RTL), about three
  minutes. The CI's fast lane (`tools/checks/text_only.py`) recognizes such a push and runs only
  those checks, then deploys, in a few minutes; any other change runs every check.
- Commit messages: English, imperative, with a short body for anything non-obvious. No
  model identifiers in commits, code or docs.
- Check the live result after a deploy: desktop and phone width (390 px), light and dark
  mode. Local screenshot checks need the CDN scripts routed to local copies (see
  `notes/HANDOFF.md`).
