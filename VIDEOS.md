# VIDEOS.md — the plan for the tutorial videos

Every question gets a tutorial video. The video walks through the solution step by step,
one chapter per part. This file is the plan: the owner's choices, the structure every
video follows, how a video is written, rendered, captioned, published and linked from its
page, the checks, and the order of work. The first two videos are pilots, 0002 and 0004.
Once their structure is approved, the rest follow it question by question.

## Why the Hebrew stays out of the frame

Manim draws text through Pango and splits it into glyphs. Right-to-left lines and lines
that mix Hebrew with code are fragile there: the order of words can flip, and so can
punctuation. The video therefore carries only what reads the same in any direction:

- code, numbers, formulas, bits and arrows;
- boxes, balls and the other objects of the question;
- nothing in Hebrew drawn by Manim: even the part's letter on the chapter card is a
  label PNG (below).

Everything said in words goes into the captions. The browser and YouTube lay out
Hebrew captions correctly, a screen reader reads them, and a wording fix needs no
re-render.

A label that must be in Hebrew inside the frame (rare: a name on a box, "אדום") is drawn
once by the browser. Playwright renders the label to a transparent PNG, and the scene
loads it as an `ImageMobject`. That is the same route the site's own figures take, so
the text is shaped right. The pilot of 0004 tests this route, because its labels are
Hebrew words. `videos/lib/he_label.py` draws each label in Rubik (the site's text font,
fetched once from Google Fonts into `videos/.cache/fonts`, with DejaVu Sans as the
fallback) at twice the frame's pixels, and caches it by text, size, colour and weight in
`videos/.cache/labels`. The pilots use it for the opening's title, level and part chips,
the chapter cards, the closing's part letters, and 0004's box labels and stamp.

## The structure of a video

A video is one file per question, with chapters. Each part of the question is one
chapter: 1–3 minutes for a part without code, 2–4 for a part with code, more when the code
is long (0004's part ב, two solutions, runs about 4.5). A short opening and closing frame the chapters. The same
skeleton serves every question; the beats inside a chapter follow the page's solution
blocks (idea → steps → code → proof → cost), so the video and the page tell the same story
in the same order.

```
0:00  Opening (15–25 s) — the DV mark drawn as on the site, the question's id, the level and the parts as chips
      Chapter א (1–3 min; 2–4 with code, more when the code is long)
        1. The problem   — the part's setting drawn (the objects, the input, what is asked)
        2. The idea      — one picture of the key insight (the "aha"), held still for a moment
        3. The steps     — the page's worked example, animated step by step; then the
                           page's box, large, played on the same example (a click marked
                           on each control it presses)
        4. The code      — typed, explained, traced: the Python answer typed live into an
                           empty panel, a caption after each line or group of lines (what
                           it does and why); then the split screen: the code moves to the
                           left, the box comes in on the right, and the run on the example
                           lights the lines in the order they run while the box steps
                           with them (the variables under the code, when there is room)
        5. Why it works  — the proof as a picture (an invariant, a table, a case split)
        6. The cost      — time and memory as two chips, and where they come from
        7. One trap      — the most common mistake, shown failing on a small input
      Chapter ב …        — the same beats; it opens with what changed from the previous part
                           (the new constraint), so the ladder of the question is visible
      Closing (10–15 s) — the parts side by side in one line each, the site's address and the
                          question's id ("try it in the box")
```

YouTube ignores a chapter shorter than 10 s, so the opening and the closing, which are
chapters of their own in `chapters.txt`, last at least 10 s (render.py checks it).

Rules for every video:

- **The page's example.** A chapter uses the example the page works by hand. A reader
  who pauses the video can find the same numbers on the page and in the box.
- **One idea per beat.** A beat ends on a still frame that holds for at least two
  seconds, so a pause lands on a readable picture.
- **The code is the page's code.** The code beat loads the code from the page's Python
  tab (`tools/extract_code.py`, without the annotation markers; `dvq.page_code()` for the
  SystemVerilog tab), so it never drifts from the tested code. Python, unless the answer is
  SystemVerilog constraints (0011). A long function may leave its comment and blank lines
  out of the picture (0004's first solution), never its code.
- **The code is typed, explained, then traced** (the owner, 2026-10-31). The code beat
  has two halves in one panel:
  1. **Typed.** `DVQScene.type_code(panel, groups)` types the function into an empty
     panel, character by character at about 16 characters a second (a seeded jitter of
     ±30 %, in the 12–20 the owner asked for), the indentation at once, a short pause at
     the end of a line. An amber bar cursor moves with the characters and blinks while
     the typing pauses. `groups` is `[(lines, caption), ...]`: a line or a few lines that
     make one operation (a loop with its body, an `if`/`else`), and a caption that says
     what it does and why; the groups cover every line in the picture, in order, or the
     render fails. After each group the typing stops, the group's lines are lit softly
     (amber, under the text), and the caption holds for reading (2–4 s, as below). A
     caption may carry animations (0002's `a ≡ v[i]`), and a group may have several
     captions.
  2. **Traced.** `run_code` runs the page's function on the example under a line tracer,
     so the lines are lit in the order they really ran, with the locals after each line
     beside the code. The variables appear only now, with a caption that names the
     example. The scene groups the traced lines under its captions, and the render fails
     if the groups differ from the trace.

  The panel never moves: `place_code` lays it out for the whole function, with the
  variables' room kept free, before the first character, and the traced run reuses it.
  A long function stays one panel, not split or scrolled, because the trace jumps between
  its loops and needs all of it in view: comment and blank lines leave the picture, and
  the code's text must be at least about 24 px (its em at 720p, `MIN_CODE_EM` = 23; the
  render fails under it). 0004's first solution, 18 lines, comes out at 24.6 px, the
  size the trace had before; the record of each scene (`out/parts/<Scene>.json`) has
  `code_em_px`. Splitting it into two panels was weighed and left out: the second half
  would hide the first while the trace still runs through it.
- **A caption per beat**, 1–2 lines: 12 words per line at most, 1.5–7 s on screen. The
  still after a beat's animations is held long enough to read its caption at about 14
  characters a second, between 2 and 4 s.
- **Colours** come from the site's palette, read from `docs/stylesheets/01-base.css` by
  the shared library (and the figure colours of `02-pages.css` and `08-explorers.css`:
  the crates and the balls of 0004), so the video matches the site. The marks on the navy
  take the dark scheme's values, made for a dark surface.
- **Fonts.** Inter for Latin text and math (its sub- and superscripts sit tight:
  `a₀`, `2³¹`), DejaVu Sans Mono for code and numbers, Rubik for the Hebrew labels.
- **The frame** is 1280×720 at 30 fps. Text is at least 28 px high, so it can be read
  on a phone. The bottom 1.5 units (about 135 px) are the captions' zone: the player
  draws the captions there, so the picture stays above it (`dvq.SAFE_BOTTOM`).
- **Math in the captions.** `captions.vtt` wraps every code or math expression of a
  caption in Unicode isolates (LRI … PDI, added by `captions.isolate()` when the file is
  written; `script.md` stays as typed). Without them a right-to-left line reorders
  expressions around their parentheses and numbers: Chromium showed `[3, 5]` as `[5 ,3]`
  and `(k + 1) % 3` with its parenthesis moved. Both the browser and libass (the burned
  preview) honour the isolates.

## The page's box

The owner asked to see the box of the page in the video (2026-10-31), so the viewer sees
the way to the answer, and the answer, the way the page shows it. The box is not redrawn:
`videos/lib/box_shots.py` captures it from the built site, and the scene shows the
pictures.

- **The spec.** `scene.py` names its boxes in the module literal `BOXES`: per name, the
  page's box (`"box": n`, the n-th `div.explorer`), the `region` (the selectors whose
  union is cropped: the figure, the player and the line that explains the step; the
  controls the box is driven by are best inside it), `hide` (a hint line inside the
  region that the video does not need) and the `steps`: one picture after each list of
  actions (`["click", sel]`, `["fill", sel, value]`, `["check", sel, bool]`, `["wait",
  ms]`; `{"do": [...], "repeat": n}` for n pictures). The format is in box_shots.py's
  docstring.
- **The capture.** `render.py` builds the site into `videos/.cache/site` (again when
  `docs/` or `hooks/` is newer), serves it, and runs box_shots.py with the Python that has
  Playwright: Chromium at 1280 px, the dark scheme (the video is navy), twice the pixels,
  the site's sticky bars hidden, the CDN scripts from `.cache/cdn`. The pictures and
  `shots.json` (each picture's file and the rectangles of the controls its step clicked)
  go to `out/boxes/<name>/`, cached by a hash of the spec, the page and the site's scripts
  and styles.
- **In the scene.** `dvq.BoxView(QID, name, height=...)` shows one picture in a thin frame.
  `self.box_step(view, k)` goes to picture k: an amber ring closes on each control the step
  clicked (a tap), then the picture changes. `self.box_beat(view, [(k, caption), ...])` plays
  the box on the example, a caption per step (the idea or steps beat).
- **The split screen.** After the code is typed, `self.split(panel, view, vp)` moves the
  panel (and the variables, under it) into the left part of the frame and fades the box in
  on the right, both as large as the room allows. `run_code(..., view=view)` takes groups
  `(lines, caption, k)`: the box steps to picture k as the group's caption appears, and the
  lines run under it. A SystemVerilog answer has no trace: `walk_code(panel, view, [(lines,
  caption, k), ...])` lights the lines of each group (the window scrolls to them) while the
  box steps. When the code's lines are too wide to share the frame (0011's constraints),
  the code of one group stands above the box instead of beside it (a panel of those lines,
  `CodePanel(code, only=...)`).
- **Readable.** The box is shown at least at 80 % of its size on the page
  (`MIN_BOX_SCALE`), and the code beside it at least 19 px (`MIN_SPLIT_EM`; typed alone it
  stays at least 23). The record of each scene lists a breach as a problem, and the render
  fails on it.
- **Long code.** A panel may be a window of `rows` lines (`CodePanel(..., rows=14)`): the
  typing scrolls it so that each group is whole in it, and the trace or `walk_code` scrolls
  it to the lines it lights. A helper that only prints (0011's `show()`) may stay out of the
  picture (`only=`), and a caption says so.

## The files

Everything for one question lives in its own folder. Shared code sits in `videos/lib`.

```
videos/
├── lib/
│   ├── dvq.py          # the shared Manim library: palette, fonts, opening/closing, chapter card,
│   │                   # code beat (typed from the page, then traced), chips, caption recorder
│   ├── captions.py     # writes captions.vtt and chapters.txt from the recorded captions
│   ├── he_label.py     # renders a Hebrew label to a transparent PNG with Playwright
│   ├── box_shots.py    # captures the page's box step by step from the built site
│   └── music.py        # generates the video's background music from a seed (numpy + ffmpeg)
├── 0002/
│   ├── script.md       # the storyboard: per chapter, per beat, the picture and the caption (Hebrew)
│   ├── captions.en.md  # the English captions: each Hebrew caption of script.md with its translation
│   ├── scene.py        # the Manim scenes, one class per chapter + Opening + Closing
│   ├── out/            # rendered, not committed: video.mp4 (silent), music.wav, music.mp3,
│   │                   # captions.vtt, captions.en.vtt, chapters.txt, parts/ (each scene's
│   │                   # recorded captions), boxes/ (the box's pictures), media/ (Manim's files)
│   └── release/        # committed (render.py --release): 0002.mp4 (silent), 0002-music.mp4,
│                       # 0002-music.mp3, 0002.he.vtt, 0002.en.vtt, 0002-chapters.txt, info.json
└── 0004/ …
```

- **The script** (`script.md`, Hebrew captions and English notes) is written first and
  reviewed by the owner before any animation is built. A video is cheap to rework at
  the script stage and expensive after the render. Its format is fixed, because
  `tools/check_videos.py` reads it (see "The script's format" below).
- **The captions are recorded while the scene plays.** Each beat calls
  `self.say("…", hold=…)`. The library writes the caption with its exact start and end
  times, as the animation really ran. Captions are therefore in sync by construction,
  with no times typed by hand. `captions.py` turns the record into `captions.vtt`, and
  into `chapters.txt`: the chapter start times, in the format YouTube reads from a
  video's description.
- **The scenes** are chained into one video with ffmpeg's concat (no re-encode), so a
  fix to chapter ב re-renders chapter ב only.
- **The English captions** (`captions.en.md`) are written once the Hebrew captions are
  final. `render.py` turns them into `captions.en.vtt`: the cues of `captions.vtt`, same
  numbers and times, with the English text (see "The translation file" below).

### The script's format

```markdown
# 0002 — swap two variables

## Opening

> שתי קופסאות : a = 5 ו-b = 3.

## Chapter א — with a temp variable

Beat 1, the problem: two boxes and a third one, t (English notes are plain lines).

> משתנה עזר שומר את הערך שהיה ב-a.
> ‏temp = a, ואז a = b, ואז b = temp.

## Chapter ב — no temp, arithmetic
...

## Closing
```

- **Chapters.** One `## Chapter …` heading per part of the question, in the page's order.
  `## Opening` and `## Closing` are not chapters. Any other heading level is free for
  notes (`### Beat 1`). The number of `## Chapter` headings must equal the page's parts.
- **Captions.** A caption line starts with `> ` (a Markdown quote), one line of the
  caption per `> ` line, so a two-line caption is two consecutive `> ` lines. Every other
  line is a note in English, and a note is never a quote. Lines inside a fenced code block
  are neither captions nor chapters.
- **Caption rules** (CLAUDE.md's RTL rules, checked line by line):
  - the text after `> ` starts with a Hebrew letter, or with the RLM mark (U+200F) when it
    must start with code, a number or Latin text;
  - every colon has a non-breaking space (U+00A0) before it and an ordinary space (or the
    end of the line) after it; a time or a ratio (1:35, 3:2), a URL and `code` in
    backticks are exempt;
  - at most 12 words per line (a word is a run of characters with a letter or a digit
    in it, so a lone colon or dash does not count).

### The translation file

`videos/<id>/captions.en.md` pairs every caption of `script.md`, in the script's order,
with its English translation:

```text
# 0002 — swap two variables: the English captions (lines starting with "#" are comments)

he: שלב 1 : temp = a. הערך 5 נשמר ב-temp.
en: Step 1: temp = a. The value 5 is saved in temp.

he: שלב 2 : a = b. עכשיו a מחזיק 3,
he: וה-5 המקורי עדיין שמור ב-temp.
en: Step 2: a = b. Now a holds 3,
en: and the original 5 is still saved in temp.
```

- **An entry** is the caption's `he:` lines, exactly as `script.md` has them (one `he:`
  line per `> ` line), then the English cue's `en:` lines. A blank line ends it. Any
  other line is an error, so a typo cannot hide.
- **The English** is natural and technically precise, the DV and CS terms as an engineer
  says them. It has one or two lines of at most 12 words and 60 characters, so it fits the
  cue's time, with no Hebrew and no direction marks. Code and math stay as they are
  (`v[i]`, `2³¹ − 1`, `(k + 1) % 3`); the parts are "Part A, B, C"; a Hebrew label drawn in
  the frame is named in English, in quotes (the box "Red and Black" of 0004).
- **The meaning** follows the page and the picture, not only the Hebrew words: the
  translator reads the page and watches the beat.
- **A change to a Hebrew caption** changes its `he:` lines too. `render.py` and
  `check_videos.py` fail when a caption has no entry, when an entry is left for a caption
  that no longer exists, or when the entries are out of order.
- **The parser and the rules** live in `videos/lib/captions.py` (`read_translations`,
  `translate`, `check_english`, `english_vtt`); `check_videos.py` loads the same module.

## Rendering

- **Tools.**
  - `manim` (Community Edition, pinned in `requirements-video.txt`, apart from the site's
    requirements so CI does not install it).
  - `ffmpeg`.
  - The Code mobject (Pygments) for the code beats.
  - No LaTeX. The pilots showed that `Text` with Unicode math (`a₀`, `2³¹`, `−`, `≡`) is
    enough, so nothing installs it. The Manim parts that call LaTeX are avoided:
    `MathTex`, `Tex`, the numbers of a `NumberLine`, `DecimalNumber`, `MathTable`,
    `BraceLabel`.
- **The command.** `~/.venvs/manim/bin/python videos/render.py 0002` (any Python with
  `requirements-video.txt`) renders the chapters at 720p30, chains them, and writes
  `video.mp4`, `captions.vtt`, `captions.en.vtt` and `chapters.txt` to `videos/0002/out/`. The flag
  `--draft` renders at 480p15 for a quick look, and `--preview` also writes
  `preview.mp4` with the captions burned in (libass, Rubik, `Encoding=-1` so the base
  direction is right to left) for a review in a plain player. The steps:
  1. **Read** `scene.py`'s `SCENES` (the scene classes in order, each with its chapter
     title for `chapters.txt`) and `script.md`'s captions, and fail early when a literal
     caption of `scene.py` is not in the script or breaks a caption rule, or when
     `captions.en.md` does not match the script. A video with no `captions.en.md` yet gets
     a warning and no English track.
  2. **Labels.** A Manim `--dry_run` lists the Hebrew labels, and `he_label.py` draws the
     missing ones in one browser session, with a Python that has Playwright
     (`--label-python`, default `python3`).
  3. **Render** every scene, then chain them with ffmpeg's concat demuxer: a stream copy
     when the scenes' parameters match (they do), a re-encode otherwise.
  4. **Captions.** Each scene's recorded captions are shifted by the real duration of the
     scene files before it. `captions.en.vtt` takes the same cues with the English text.
  5. **Music.** `lib/music.py` generates the piece for the video's exact length into
     `out/music.wav`, and it is muxed into `video.mp4` (the video stream copied, the music
     as AAC at 160 kbps). The preview copies that soundtrack. `--no-music` skips it.
  6. **Fail** on a caption under 1.5 s or over 7 s, a line that breaks the RTL or colon
     rules, a beat whose still is under 2 s, a chapter under 10 s, captions that differ
     from `script.md` (text, line breaks or order), or a scene whose recorded length
     differs from its file. It prints the length, the size, the chapters and the
     `video_parts` for the front matter (the first part at 0, as the checks want: the
     link to part א plays the opening too).
  A pilot renders in about 3–5 minutes as a draft and 15–20 minutes at 720p30 since the
  code is typed (every typed character is a frame Manim draws; the two pilots in
  parallel on four cores).
- **The English track alone.** `python videos/render.py 0002 --captions-only` renders
  nothing: it writes `out/captions.en.vtt` from the existing `out/captions.vtt` (its cues
  and times) and `captions.en.md`, in a second, with any Python. It is the command after
  a fix to the English. It fails when `captions.vtt` no longer matches `script.md` (render
  the video again first) or when the translation file does not match the captions.
- **The music alone.** `python videos/render.py 0002 --music-only` (with the Manim venv:
  it needs numpy) renders no scene: it regenerates `out/music.wav` for the length of the
  existing `out/video.mp4` and remuxes it into `video.mp4` and, when it exists,
  `preview.mp4`, replacing their old soundtrack. About two minutes for a five-minute video.
- **Rendering stays local.** It does not run in CI: Manim and LaTeX are heavy, and the
  MP4 is not served from the site.

## The music

The owner asked for calm background music in every video, in the spirit of the math-proof
videos on YouTube: soft, reflective, a piano over an ambient pad, and a different piece in
each video. Downloading music is not an option (the network blocks the music sites, and a
licence or a Content ID claim on YouTube is a risk), so the music is **generated**:
`videos/lib/music.py` renders it from a seed with numpy, and ffmpeg sets its loudness. The
piece is ours, with no licence to track and nothing for Content ID to match.

- **The piece.**
  - A slow progression of 4–8 chords from a curated list of nine (`PROGRESSIONS`: maj7,
    maj9, add9, 6/9, sus and minor 7/9/11 colours in Ionian, Lydian or Dorian), 8 beats a
    chord (5–7.5 s). It loops with variations: a chord's colour swapped for a neighbour
    that stays in the mode, the arpeggio's inversion shifted or turned downwards, notes
    left out, and every fourth pass breathes with fewer notes. The chord length is
    stretched slightly so whole passes end where the closing tonic chord starts, about
    9 s before the end.
  - A pad: three detuned voices of a band-limited saw/triangle blend (a wavetable from its
    harmonics, through a gentle low-pass), slow attack and release, a slow drift of
    brightness.
  - A soft piano: additive partials with slight inharmonicity, two strings a partial, a
    4 ms attack, a two-stage exponential decay, the velocity setting the brightness,
    humanised timing.
  - A sub-bass on the roots (in most seeds).
  - A reverb: a convolution with a synthetic decaying-noise impulse response of 2.6–3.4 s,
    a different noise for each ear, which gives the stereo width.
  - A 3 s fade-in and a 4 s fade-out that end exactly at the video's last frame.
- **The seed** is the question's id (or `MUSIC_SEED = <int>` in `scene.py`, to pick
  another piece without touching the library). The progression and its mode, the key and
  the piano's pattern rotate with the seed by multipliers prime to their counts, so
  consecutive ids differ in all three. A random generator on the seed picks the tempo,
  the instrument mix, the reverb and every humanised detail. `python videos/lib/music.py
  --seed 4 --describe` says what a seed plays. The pilots:
  - 0002: Bb Lydian, `Bbmaj7#11 – Cadd9 – Gm9 – Fadd9`, a rising arpeggio, about 66 bpm;
  - 0004: A Dorian, `Am9 – Dadd9 – Cmaj7 – G6/9`, a sparse arpeggio, about 67 bpm.
- **Loudness.** ffmpeg's `loudnorm` in two passes (measure, then a linear gain) to
  **-28 LUFS** integrated, true peak under -2 dBTP. The first pilots were at -24 LUFS; the
  owner asked for softer music, with less pad and bass and more piano (2026-10-31), so the
  piano now leads at about 2.2–2.7× the pad's level, the pad is darker (a 700–1100 Hz
  low-pass) and a sub-bass, in half the pieces, is a hint. The narration, when it comes,
  sits near -16 LUFS, about 12 dB above the music.
- **The checks** (`music.py --analyse out/music.wav --spectrum m.png`, and printed by
  `render.py`): the integrated loudness and the true peak by `ebur128`; clicks, as the
  largest sample-to-sample step against the RMS (the pilots: 0.46–0.59) and the count of
  second-difference spikes over 12 times their local RMS (0); a spectrogram by
  `showspectrumpic` (nothing above about 6.5 kHz, no noise floor).

### Mixing the narration later

The voice is not built yet. When it is, it is normalised to -16 LUFS and ducks the music
by about 5 dB while it speaks (`sidechaincompress`, keyed by the voice), then the two are
mixed. Tested on the pilots' music with a test tone as the voice: -4.9 dB under the voice,
back to 0 dB about half a second after it stops.

```bash
ffmpeg -i out/video.mp4 -i voice.wav -filter_complex "
  [1:a]aresample=48000,aformat=channel_layouts=stereo,
       loudnorm=I=-16:TP=-1.5:LRA=11,aresample=48000,asplit=2[voice][key];
  [0:a][key]sidechaincompress=threshold=0.07:ratio=3:knee=4:attack=60:release=500:makeup=1[ducked];
  [ducked][voice]amix=inputs=2:duration=first:normalize=0,
       alimiter=limit=0.89:level=disabled[mix]" \
  -map 0:v -map "[mix]" -c:v copy -c:a aac -b:a 160k out/video-voice.mp4
```

- `threshold` and `ratio` set the depth: 0.1 and 3 give about 3 dB, 0.05 and 4 about
  8 dB. `release` (ms) is how fast the music comes back after a sentence.
- A two-pass `loudnorm` of the voice file first (as `music.py` does) is steadier than
  the one-pass filter above; the one-pass form keeps the graph self-contained.
- The voice track sets the captions' timing then (Open points, "Voice").

### Options considered

- **Licensed or free-licence tracks** (YouTube Audio Library, Creative Commons): blocked
  by the network here, a licence to keep per track, and a Content ID claim is still
  possible on shared tracks.
- **One shared piece for every video**: simpler, but the owner wants a different piece
  per video; the seed gives that at no cost.
- **Louder music (-20 LUFS)** or **none under the voice**: -28 LUFS plus about 5 dB of
  ducking keeps the music audible alone and clearly under the voice.

## Publishing and linking

0. **The release.** `render.py <id> --release` (720p, with no problem) copies the finished
   files into `videos/<id>/release/`, and `python tools/catalog.py` puts their download
   links into the README's "Tutorial videos" table (the length and the files, from
   `release/info.json`). The folder is committed; that is where the owner takes the
   videos from (2026-10-31).
1. **Upload.** The owner uploads `<id>.mp4` (or `<id>-music.mp4`, or the video edited with
   `<id>-music.mp3`) to the YouTube channel. Unlisted or public is the owner's call per
   video.
2. **Captions and chapters.** In YouTube Studio, under the video's Subtitles:
   - set the video's language to Hebrew;
   - add a language, Hebrew, and upload `<id>.he.vtt` as a file "with timing";
   - add a language, English, and upload `<id>.en.vtt` the same way;
   - leave both tracks off by default: do not set either one as the default track, and do
     not turn captions on for the video. The viewer picks a track in the player's settings;
   - paste `<id>-chapters.txt` into the description (YouTube makes chapters from it).
3. **The page.** The video id and the chapter times go into the page's front matter:

   ```yaml
   video: dQw4w9WgXcQ          # the YouTube id
   video_parts: [0, 95, 210]   # the start of each part's chapter, in seconds
   ```

   The id is quoted when YAML would read it as a number or a boolean. A page with one
   part may leave `video_parts` out. The build, `lint_pages.py` and `check_videos.py`
   all reject a bad id, a missing time, a count that differs from the page's
   `### סעיף` headings, a first time other than 0, or times that do not rise.
   Then `python tools/catalog.py` turns the README's "Tutorial videos" row of that
   question into a YouTube link. The table has a row per `videos/<id>/script.md`, and a
   test checks that it is up to date.
4. **The hook** (`hooks/questions.py`) does the rest:
   - **The page tool.** A "סרטון הסבר" icon button (a screen with a play triangle) first
     among the page tools of the header card. Practice mode hides it with the solutions.
   - **The chapter links.** A "לפרק בסרטון 1:35" pill at the top of the first solution
     block of each part, right under its summary, so it shows only to a reader who
     opened the solution. On a page without parts the one link reads "לסרטון ההסבר".
     Its `href` is the video on youtube.com at that time, for a reader without the script
     or one who opens it in a new tab.
5. **The dialog** (`docs/javascripts/video.js`, `docs/stylesheets/20-video.css`):
   - **A native `<dialog>`, modal.** It is titled "סרטון הסבר : <the question's title>"
     and the focus moves to the play button. Tab and Shift+Tab cycle inside it. Esc,
     the × button and a click on the backdrop close it, and the focus returns to the
     button or link that opened it.
   - **The poster.** The site's navy with a faint grid, two amber traces and the
     question's id and title, an amber play disc and the start ("הפעלה מסעיף ב · 1:35").
     It is CSS only, the same in both schemes. Nothing comes from YouTube until the
     reader presses play: no request, no thumbnail, no cookie, and the page keeps its
     weight.
   - **Chapter buttons.** Above the stage, one per part ("סעיף ב 1:35"), the chosen one
     amber. Before play they move the poster's start; while playing they restart the
     player at that part.
   - **The player.** Play puts an iframe in the poster's place:
     `https://www.youtube-nocookie.com/embed/<id>?start=<s>&hl=he&rel=0&modestbranding=1&autoplay=1`,
     titled like the dialog, with `allow="autoplay; encrypted-media; picture-in-picture; fullscreen"`
     and `allowfullscreen`. Closing removes the iframe, which stops the video.
   - **The size.** The stage is 16:9, as wide as the screen allows up to 60rem and short
     enough for a landscape phone. Under 30em the dialog runs edge to edge.
   - The page checks run offline, so they never load YouTube; `check_keyboard.py` cuts
     the player's request off when it presses play.

## Checks

- **`tools/check_videos.py`** runs in CI's test job, after the lint, and needs no video.
  For every question with a `video:` field:
  - the id has the YouTube form;
  - `video_parts` has one time per part, rising from 0;
  - `videos/<id>/script.md` has one `## Chapter` heading per part of the page. A page
    whose script does not exist yet gets a warning, not a failure.

  For every `videos/*/script.md`, every caption line (`> …`) follows the caption rules
  above. When `captions.en.md` exists beside it, every caption has an English entry
  there, in order, no entry is left for a caption that no longer exists, and the English
  follows its rules (two lines of 12 words at most, no Hebrew).

  Its tests are in `tests/tools/test_check_videos.py`, and the hook's in
  `tests/hook/test_hook.py` (a page with a fake id, never a real page).
- **The page checks** must stay green: `check_phone`, `check_keyboard` and axe. The dialog
  is checked as a component by `check_keyboard.py`, on the first question page with a
  video: Enter opens it with the focus inside, Tab and Shift+Tab stay in it, its buttons
  are named, Esc closes it and gives the focus back, and play makes a titled iframe that
  the close button removes.
- **`render.py`** stops on a caption shorter than 1.5 s or longer than 7 s, on a beat
  with no still frame of 2 s at its end, on a chapter under 10 s, and on captions that
  differ from `script.md`, and on a `captions.en.md` that misses a caption or keeps an entry
  for one that no longer exists (see "Rendering").

## The pilots' storyboards (outline; the full scripts are step V2 and V4)

**0002 — swap two variables (three parts, 7:26 in all)**

- **Opening.** Two registers `a = 5` and `b = 3` (the page's example), shown as boxes with
  their bits.
- **Chapter א — with a temp variable.**
  - A third box `t`; the three moves animated; the values travel as cards.
  - Code: the three lines typed one by one, each with its caption, then lit in turn.
  - Why it works: each value always sits in at least one box.
  - Cost: O(1) time and one word of memory.
  - Trap: the order of the moves, shown failing when the first move is lost.
- **Chapter ב — no temp, arithmetic.**
  - The new constraint is struck out on the chapter card: the `t` box fades away.
  - `a = a + b`: the sum appears; then the two subtractions recover each value.
  - A number line shows why no information is lost.
  - Overflow: the 32-bit wheel (mod 2^32) turns past the top and still comes back right.
  - Trap: `swap(x, x)`, the same variable twice, giving 0.
- **Chapter ג — bitwise only.**
  - The same three steps with `^`, on 4-bit columns: a bit flips where the column has a 1.
  - The XOR rules as a 2×2 table.
  - The proof: each bit column separately.
  - Trap: the same address again, and why `&` or `|` lose information (a column that can
    no longer be undone).
- **Closing.** Three lines side by side: temp / sum / XOR.

**0004 — three mislabeled boxes (two parts, 6:54 in all)**

- **Opening.** The three boxes with their Hebrew labels (`he_label.py`) and the rule "all
  labels are wrong" as a red stamp.
- **Chapter א — the minimum number of draws.**
  - The six ways to fill the boxes shrink to the two in which every label is wrong (a
    permutation table with the fixed points struck out).
  - Drawing from a red or a black box can leave two cases open; drawing from "mixed"
    cannot.
  - One draw, so the answer is 1, and zero draws is not enough.
  - Both cases are played out: a red ball, then a black ball.
- **Chapter ב — the code.**
  - `draw(i)` as a hand taking one ball.
  - The first solution: find the box labelled MIXED, draw once, and fill a new label
    array in three passes by part א's rule. It is typed group by group (a caption per
    loop, the draw, the `if`/`else`), then its lines are lit for a red result, then for a
    black one.
  - The page's second solution: the fix is a rotation of the three labels, shown as the
    labels sliding one box over. Two swaps in place do it, with no new array. The code is
    typed the same way, then traced with a red ball.
  - The index arithmetic: `(k + 1) % 3` and `(k + 2) % 3`, and why `(k - 1) % 3` differs
    between Python and SystemVerilog for k = 0.
  - Cost: O(1).
- **Closing.** One draw from the "mixed" box fixes all three labels.
